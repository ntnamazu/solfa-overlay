- ステータス: ドラフト（承認待ち）

## プロダクト概要

### 名称

**Solfa Overlay（仮称）** - 合唱楽譜PDFへの移動ド階名自動付与アプリ

### プロダクトコンセプト

- **元の版面へのオーバーレイ**: 楽譜を再組版せず、購入した楽譜のPDFそのものに階名を重ね書きする。練習現場で死活的に重要な「みんなと同じ版・同じページ割・練習番号」を完全に保つ
- **自動＋人間の確認・修正**: OMR（光学的楽譜認識）の精度限界を前提に、壊滅的エラーを安価に捕捉する確認UIと、局所エラーを補う修正UIを体験設計の中心に置く
- **ローカル完結**: 楽譜データをサーバーに一切保存・送信しない。著作権リスクと運用コストを同時にゼロに近づける

### プロダクトビジョン

合唱を歌う人が、書店で買った楽譜をスキャンして読み込ませるだけで、全音符に移動ドの階名が振られた「そのまま印刷して練習に持っていける」楽譜を手に入れられる世界を実現する。手書きで階名を書き込む機械的な作業から歌い手を解放し、階名唱による楽曲理解という本質的な活動に時間を使えるようにする。将来的には各音の和音内での役割（根音・第三音等）も表示し、合唱ならではの和音の鳴らし方を楽譜の上に直接落とし込めるようにする。

### 目的

- 合唱譜への移動ド階名の手書き書き込み作業（1曲あたり十数分〜数十分の機械的作業）を自動化し、歌い手の作業を確認・修正のみにする
- OMRの誤認識による誤った階名を、確認UIによってユーザーが実用上問題ないレベルまで排除できるようにする
- 「階名の自動付与を製品として提供するアプリが存在しない」という市場の空白を埋める

## ターゲットユーザー

### プライマリーペルソナ: 高階 信弘（40代、アマチュア混声合唱団員・ソフトウェアエンジニア）

- 趣味で混声合唱を継続しており、相対音感を活かして楽譜を移動ド（短調はLa基準、コダーイ式音節）で読解・視唱している
- 新曲を渡されるたびに、調号から各音符の階名を解き明かして音符の横に手書きメモしている。1曲あたり十数分〜数十分かかる完全にルールベースの機械的な作業を、新曲のたびに繰り返している
- PCとコマンドラインの操作には習熟しているが、日々のワークフローに組み込むなら GUI で完結してほしい
- 期待する解決策: スキャンPDFを入力すると、数十箇所の確認と数箇所の修正だけで、印刷可能な階名付きPDFが得られること
- 典型的なワークフロー: 練習で新曲の楽譜を受け取る → 自宅でスキャン → 階名を付与 → 印刷して次回練習に持参

### セカンダリーペルソナ: 階名唱を練習したい一般合唱団員（20〜60代）

- 音楽理論の素養は基礚レベル。「移動ドで歌うと音が取りやすい」と聞いて階名唱を練習したいが、自力で階名を振るのはハードルが高い
- ソフトウェアのインストールや複雑な設定は苦手。ツールチェーン（Audiveris → MuseScore → プラグイン）を自分で組むことは現実的に不可能
- 期待する解決策: 専門知識なしで使える、ワンストップの階名付与アプリ

## 成功指標(KPI)

### プライマリーKPI

- **作業時間の短縮**: 10ページ以内の楽譜1曲について、読み込みから印刷可能PDFの取得までを確認・修正作業込みで15分以内に完了できる（手書きの所要時間 十数分〜数十分 を確実に下回る。かつ手書きと異なり機械的作業がユーザーの手から離れる）
- **階名付与カバレッジ**: きれいな印刷譜のスキャンにおいて、確認・修正フロー通過後の階名付与率 98%以上（プロトタイプ実測: 修正前で約98%＝5小節欠落/約296パート小節）
- **音高の正確性**: 確認UI通過後（音部記号・調号確認後）の階名誤り率 1%未満（プロトタイプ実測: 音高照合ミスマッチ 0/784音）

### セカンダリーKPI

- **発案者自身の実利用**: 自身の合唱団の全新曲（年間数曲〜十数曲）でこのアプリを使い、手書きに戻らないこと（v1リリース後6ヶ月間）
- **外部ユーザーの獲得**: 所属合唱団内・階名唱コミュニティでの利用者 10人（v1リリース後6ヶ月）
- **確認UIの有効性**: 系統的エラー（音部記号・調号・譜表構造の誤認識）の見逃しによる「段全体が誤った階名」の発生ゼロ

## 機能要件

### コア機能(MVP / v1)

#### F-1: 楽譜PDFの読み込みとOMR実行

**ユーザーストーリー**:
合唱団員として、購入した楽譜を階名付与の対象にするために、スキャンしたPDFをアプリに読み込ませて自動認識させたい

**受け入れ条件**:
- [ ] スキャンされた楽譜PDF（複数ページ）を入力として受け付ける
- [ ] Audiveris によるOMRを内部で実行し、MusicXML（解析用）と .omr（座標用）を取得する
- [ ] OMRの進捗が画面に表示される
- [ ] 楽譜データ（PDF・中間データ・出力）が外部サーバーに送信されないことを保証する
- [ ] インチピット等により譜表構造が誤分割された場合（プロトタイプで実際に発生）に、book.xml の movement 情報から復元する、または確認画面でユーザーが統合を指示できる

**優先度**: P0(必須)

#### F-2: 音部記号・調号の確認画面

**ユーザーストーリー**:
合唱団員として、段全体が全滅する系統的な誤りを防ぐために、階名生成の前に検出された音部記号と調号の一覧を確認・修正したい

**受け入れ条件**:
- [ ] 検出された全譜表の音部記号・調号を、元画像の該当箇所の切り抜きと並べて一覧表示する
- [ ] ユーザーが誤認識を修正できる（特にテノールの「オクターブ下ト音記号」の指定）
- [ ] 1曲（10ページ以内）あたりの確認作業が5分以内に完了する分量・UIである
- [ ] 確認完了後にのみ階名生成へ進める

**優先度**: P0(必須)

#### F-3: 移動ド階名の計算

**ユーザーストーリー**:
合唱団員として、自分の流儀で階名唱するために、全音符に対して移動ドの階名を自動計算してほしい

**受け入れ条件**:
- [ ] 内部表現は「スケール度数＋変位」で持ち、表示時に文字列化する（音節体系と短調基準の2軸が直交する設計）
- [ ] 短調は **La基準** をデフォルトとし、設定で Do基準（me/le/te 使用）に切替できる
- [ ] 音節体系は **コダーイ式**（do, di, re, me 等）をデフォルトとし、設定で Tonic sol-fa略記（d, r, m, f, s, l, t ＋ ta, fe 等）に切替できる
- [ ] 臨時記号による半音変化を各音節体系の規則どおりに反映する（プロトタイプで Tonic sol-fa略記の de/ta/fe/se の付与を検証済み。コダーイ式でも同一の内部表現から文字列化する）
- [ ] 調号の変更（明示的な転調）に自動追従する

**優先度**: P0(必須)

#### F-4: 注釈付きPDFの出力（オーバーレイ描画）

**ユーザーストーリー**:
合唱団員として、練習でみんなと同じ版・同じページ割の楽譜を使うために、元のPDFの版面に階名が重ね書きされた印刷可能なPDFが欲しい

**受け入れ条件**:
- [ ] 元PDFの版面・ページ割を一切変更せず、.omr の記号座標を用いて各符頭の近傍に階名を描画する
- [ ] 幹音と半音変化した音が色または書体で区別できる
- [ ] 階名の書体は小サイズでも判読できるものを選定する（Helvetica の小文字「l」の視認性問題をプロトタイプで確認済み）
- [ ] モノクロ印刷でも判読できる
- [ ] A4印刷で実用に足る解像度・配置品質である

**優先度**: P0(必須)

#### F-5: 階名の手動修正UI

**ユーザーストーリー**:
合唱団員として、OMRの局所的な誤りを埋めるために、欠落・誤りのある階名を楽譜画像の上で直接修正・追加したい

**受け入れ条件**:
- [ ] 音符数不一致等でスキップされた小節が一覧で提示され、該当箇所へジャンプできる
- [ ] 楽譜画像上の任意の位置に階名注釈を追加・編集・削除できる
- [ ] 修正結果が出力PDFに反映される
- [ ] 修正状態（注釈レイヤーの中間データ）をファイルとして保存・再読み込みできる

**優先度**: P0(必須)

#### F-6: 転調点の指定・修正UI

**ユーザーストーリー**:
合唱団員として、調号が変わらない一時転調や自分の解釈に沿った読み替えを反映するために、転調点と解釈先の調を自分で指定・修正したい

**受け入れ条件**:
- [ ] 楽譜上の任意の位置（小節・拍）を転調点として指定し、以降（または指定範囲）の解釈先の調を設定できる
- [ ] 指定に応じて該当範囲の階名が再計算される
- [ ] 自動検出された調号変更点も同じUI上に表示され、上書き修正できる
- [ ] 転調点の指定は保存され、再出力時に維持される

**優先度**: P1(重要)

### 将来的な機能(Post-MVP / v2)

#### F-7: 和音役割レイヤー

各音が和音の根音・第三音・第五音・第七音・第九音等のいずれであるかを、階名レイヤーとは独立した注釈として表示する。合唱における和音の鳴らし方（根音はしっかり、第三音は控えめに等）を楽譜上に直接落とし込める、競合不在の機能。

- 和音役割は調にも階名設定にも依存しないため、独立したレイヤーとして設計する
- 非和声音（経過音・掛留・倚音）の判定は本質的に曖昧であるため、確信度が低い箇所は表示を控える、または「?」を付ける誠実な設計とする
- 音価（リズム）認識への依存度が高く、OMR品質への要求が階名より厳しいため v2 に後置する

**優先度**: P2(できれば)

#### F-8: レイヤー表示切替・出力カスタマイズ

階名レイヤー／和音役割レイヤーの表示・非表示、色、配置の設定。パート別の出力（自分のパートのみ階名を付与する等）。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス

- OMR〜階名計算〜PDF出力の全処理: 10ページの楽譜で10分以内（一般的なPC環境。OMRが支配的）
- 確認・修正UIの操作レスポンス: 画面遷移・注釈編集とも1秒以内
- 修正後のPDF再出力: 30秒以内

### ユーザビリティ

- セカンダリーペルソナ（非エンジニアの合唱団員）が、説明書なしで最初の1曲を完了できる導線を持つ
- 確認画面（F-2）は1曲あたり5分以内で完了できる分量に収める
- UI言語は日本語（v1）

### 信頼性

- ユーザーの修正作業（F-5, F-6）が中間データとして永続化され、アプリ再起動後も失われない
- OMRが失敗した場合（認識不能なページ等）でも、失敗箇所を明示して部分的な結果を提供する（全体を失敗にしない）

### セキュリティ・プライバシー（著作権対応）

- 楽譜データ（入力PDF・中間データ・出力PDF）を外部サーバーに一切保存・送信しない**ローカル完結設計**（デスクトップアプリ、またはWASMによるブラウザ内ローカル処理）
- ネットワーク通信が発生する場合（アップデート確認等）も、楽譜由来のデータを含めない

### スケーラビリティ

- 楽譜の規模: 50ページ・8パート程度までの楽譜を処理できる
- 1曲あたりの注釈数: 5,000音程度まで修正UIの操作性が劣化しない

## スコープ外

明示的にスコープ外とする項目:

- **楽譜の再組版**: MusicXMLからの楽譜再レンダリングは行わない（オーバーレイ方式に限定）
- **リズム・歌詞・強弱等の認識結果の修正機能**: 階名付与に不要な要素の誤認識は修正対象としない
- **音源再生・MIDI出力**: 演奏機能は提供しない
- **クラウド保存・共有機能**: 著作権対応の設計方針（ローカル完結）に反するため提供しない
- **固定ドや音名（CDE/ハニホ）表記**: v1では移動ド階名に限定する
- **手書き楽譜・低品質スキャンへの対応保証**: きれいな印刷譜のスキャンを前提とする
- **モバイルアプリ**: PC環境（デスクトップまたはブラウザ）に限定する
