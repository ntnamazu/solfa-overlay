# アイデアメモ: 確認画面の表示文字を「合唱団員の語彙」に寄せる

- 記録日: 2026-07-29
- ステータス: **方針決定済み・未実装**。実装は別途ステアリングファイルを起こして行う
- 発案者: Nobuhiro Takaichi
- 位置づけ: 壁打ち成果物。確認画面（StructureConfirm / ClefKeyConfirm）の表示文字が読み取りづらい問題について、原因の切り分けと対処方針を記録する。用語の正式な定義は [glossary.md](../glossary.md) を正とし、本メモはそこへ何をどう追記するかの根拠を残す

## 1. 一言で言うと

確認画面に `P1` / `TREBLE` / `UNKNOWN` / `(1, 1, 1, 1, 4, 4)` といった**内部識別子と裸の数値がそのまま出ており**、ユーザーが意味を推察しないと読めない。**「アプリの語彙」を「合唱団員の語彙」へ翻訳する**ことで、認知負荷を下げる。

調査の過程で、単なる文言の問題ではなく **「表示が実態と食い違っている箇所」（`UNKNOWN` の食い違い件数 0）** が見つかったため、そこも併せて対処する。

## 2. 調査対象

`tmp/example-projects/` の実プロジェクト 4 件（`civabit-eos` / `o-quam-gloriosum` / `christus-factus-est` / `dolcissima-mia-vita`）の `project.json` を展開し、画面表示の元になる値を実測した。

## 3. 課題の切り分け

見た目はバラバラの問題だが、原因は 3 つに集約できる。

| #   | 原因                                                         | 該当箇所                                                            |
| --- | ------------------------------------------------------------ | ------------------------------------------------------------------- |
| ①   | **内部識別子がそのまま画面に出ている**                       | `P1`〜`P5`、`TREBLE`、`UNKNOWN`、`TREBLE_DOWN_8`                    |
| ②   | **数値に単位・文脈がない**（多いのか少ないのか判断できない） | 「音高の不一致 3」「対象の段数 10」「(1, 1, 1, 1, 4, 4)」           |
| ③   | **その画面で何をすればよいかが書かれていない**               | 譜表構造の確認画面（全行が「—」になり操作の余地がない状態が起こる） |

## 4. 調査で分かった事実（対処方針の根拠）

### 4.1 `P1`〜`P5` は「段の中で上から何番目のパートか」

`score.parts[].staves[].staffIndex` の実測値:

| プロジェクト        | P1  | P2  | P3  | P4                | P5  |
| ------------------- | --- | --- | --- | ----------------- | --- |
| civabit-eos         | 0   | 1   | 2   | 3                 | —   |
| dolcissima-mia-vita | 0   | 1   | 2   | 3                 | 4   |
| o-quam-gloriosum    | 0   | 1   | 2   | **0 と 3 が混在** | —   |

「楽譜の上から N 番目」という推察は妥当。ただし本プロジェクトの用語では **「段」＝システム（横 1 行のまとまり）** であり（[glossary.md](../glossary.md) 「システム（段）/ 譜表 / 小節」）、`staffIndex` は**段の中での上下位置**を指す。UI で「1段目〜4段目」と書くと段番号と衝突するため、「上から N 番目のパート」と表現する。

### 4.2 「上から何番目か」を staffRef の最初の要素から決めてはいけない

`o-quam-gloriosum` の P4（実体はバス）の `staffRefs` 先頭は `(page 0, system 0, staffIndex 0)` である。1 ページ目のインチピットが 1 パートだけの段として誤検出され、それが P4 に割り当てられているためで、**「最初に現れた `staffIndex`」で並べるとバスが最上段に表示される**。

対処として `partId` の昇順を採用する。ただし現行の `confirmationItems.ts` は `a.partId.localeCompare(b.partId)` を使っており、パートが 10 以上になると `P10 < P2` と並ぶ。**自然順（数値部分を数値として比較）へ修正する**。

### 4.3 音部記号は階名の計算には使われていない（クロスチェック専用）

`ScoreModelBuilder` の `matchStack` では、音符の音高は **MusicXML 由来**（`pitch: xmlNote.pitch`）で決まる。`clefKind` の用途は `headStepOctave(head.pitch, clefKind)` ただ 1 箇所で、**「.omr の譜表位置から逆算した音名」と「MusicXML の音名」を突き合わせる検算**にしか使われない。

### 4.4 【重要】`UNKNOWN` の「食い違い 0」は「問題なし」を意味しない

`UNKNOWN_CLEF` は、`.omr` の sheet XML にその五線に対応する `<clef kind="...">` が 1 つも無かったときに付く値（`confirmationItems.ts` の `staff.clefKind ?? UNKNOWN_CLEF`）。**楽譜に音部記号が無いのではなく、Audiveris が読み取れなかった**ことを表す。

このとき `clefTable.ts` の `headStepOctave` が

```ts
if (clefKind === null) {
  return null;
}
```

で即座に `null` を返すため、**クロスチェックそのものが行われない**。結果として `mismatchCount` は 0 のままになる。

さらに `ScoreModelBuilder` が `unknownClef` を報告する条件は `clefKind !== null && !isKnownClefKind(clefKind)` であり、**「何も検出できなかった」場合は報告すら出ない**。

したがって現在の画面では次の 2 つが同じ「0」に見えている:

| 表示                 | 実際の意味                               |
| -------------------- | ---------------------------------------- |
| ト音記号 ／ 不一致 0 | 検算した結果、食い違いが無かった         |
| UNKNOWN ／ 不一致 0  | **検算していないので何も分かっていない** |

`civabit-eos` では計 5 譜表（P1 が 2ページ1段目・4段目、P2 が 2ページ1段目・2段目、P4 が 1ページ3段目）がこの状態で、曲の途中に散在している。インチピットのような構造的理由ではなく単純な検出漏れと見られる。

実害は「階名が誤る」ことではなく（音高は MusicXML 由来なので誤らない）、**「誤っていないことの保証が無い」**という点にある。ただし [glossary.md](../glossary.md) は音部記号の誤検出を「確認画面の最重要チェック項目」と位置づけており、その検算が黙って無効化されたまま「0 件」と表示するのは実態と食い違う。

### 4.5 並び順は「実装されていない」のではなく「凍結されている」

`confirmationItems.ts` は `不一致件数の降順 → partId 昇順 → 検出値昇順` でソートしている。一方 `mergeCorrections` が「初回に提示した並びをセッション中固定する」ため、**初回解析時に不一致が 0 件だった場合は `partId` 昇順（＝楽譜順）のまま凍結される**。

`dolcissima-mia-vita` は不一致 7/1/0/8/2 を持ちながら `P1→P5` の楽譜順で並んでいる。初回解析時は構造のズレで小節が `skipped` となりクロスチェックが走らず、全件 0 のまま並びが凍結されたためと考えられる（`structureDecisions` に 2 件の訂正が残っている）。

つまり現状は **「初回解析時にたまたま不一致が出たかどうか」で並び順の意味が変わる**。ユーザーが法則を学習できないため、楽譜順に固定することで並びの意味を一定にする。

### 4.6 `(1, 1, 1, 1, 4, 4)` の正体

`o-quam-gloriosum` のページごとの「段あたりのパート数」実測値:

| ページ    | 段ごとのパート数     |
| --------- | -------------------- |
| 1ページ目 | **1, 1, 1, 1, 4, 4** |
| 2ページ目 | 4, 4, 4              |
| 3ページ目 | 4, 4, 4, 4           |

1 ページ目の最初の 4 つの「段」がパート 1 つしか持たない。[glossary.md](../glossary.md) の「インチピット」に記載された既知の系統的エラー（インチピットが原因で第1システムが独立譜表に誤分割される）と一致する。**アプリ側に概念と名前があるのに、画面ではそれに触れていない**。

### 4.7 用語集に実装とのズレがある

[glossary.md](../glossary.md) 「オクターブ下ト音記号」の英語表記欄が

> コード内の検出値: `'G-clef-8vb'`、UIのドロップダウン表記: G-8vb

となっているが、`G-clef-8vb` はリポジトリ全体で**この 1 行にしか存在しない**。実装は `TREBLE_DOWN_8`（`SELECTABLE_CLEF_KINDS` / `clefTable.ts`）。プロトタイプ時代の記述が残ったものと見られる。用語集は「コード内の識別子は本用語集の英語表記に統一する」と宣言しているため、**用語集に従うと壊れる**状態になっている。

## 5. 用語の整理: なぜ「譜表」ではなく「パート」と呼ぶか

### 5.1 三者はふだん一致しているだけ

合唱団員の日常語の「パート」は、`staff`（五線 1 組）とも MusicXML の `part`（論理的な声部）とも一対一ではなく、**「同じ 1 本の線を担当する歌い手／奏者の集団」という社会的な単位**である。

| 場面                                             | 日常語の「パート」が指すもの                        |
| ------------------------------------------------ | --------------------------------------------------- |
| トップ／セカンドテノールを「テノール」と総称する | 1 つの**譜表**（2 声部が 1 本の五線を共有する場合） |
| ピアノ伴奏者を「ピアノパート」と呼ぶ             | 2 つの**譜表**（大譜表＝1 つの `part`）             |
| 合唱の開離譜（SATB が各 1 段）                   | **三者が一致**（1 譜表 = 1 声部 = 1 パート）        |

v1 の対象は最後のケースであり、そこでは三者が一致する。**だから UI で「パート」と呼んでよい**。

用語集に書くべきは「パート＝譜表」という同一視ではなく、**「v1 の対象範囲では一致する」という条件つきの記述**である。条件を明記しておけば、将来 2 段譜やピアノ伴奏を扱うことになったときに「どの前提が破れたか」が即座に分かる。

### 5.2 MusicXML・ドメインモデル・日常語の三点一致

```
MusicXML の語彙            ドメインモデル                  合唱団員の日常語
─────────────────────────────────────────────────────────────────────
<score-part id="P1">   →   Part { id, name, staves }   →   「パート」
  （論理的な声部）              ScoreModel.ts                 「パート練習」
<staff>                →   StaffRef {page,system,idx}  →   「◯段目」
  （物理的な五線）
```

`Part.id` は「MusicXML part id（= book.xml logical-id）」であり、MusicXML の規格自体が part（論理）と staff（物理）を区別している。ドメインモデルもそれを踏襲している。

したがって今回の変更は用語の**翻訳**ではなく、**すでにモデルにある正しい名前を画面に出す**作業である。現在の `P1` 表示は「『パート』という名前があるのに内部 ID の方を見せてしまっている」状態にすぎない。

なお `Part`（論理）と `StaffRef`（物理）はモデル上分かれたままなので、UI 用語を「パート」に統一してもモデルは破綻しない。将来 5.1 の前提が崩れたときに見直すのは **UI 用語だけ**でよい。

## 6. 決定した方針

### 6.1 語彙

- **「譜表」を UI に出さない**。「パート」と表示する
- **「システム」を UI に出さない**。「段」と表示する（練習現場の「2段目の4小節目から」という言い方に合わせる。指揮者の号令の語彙がそのまま使える）
- 音部記号は**日本語のみ**を表示し、内部値（`TREBLE` 等）は画面に出さない
  - 根拠: [product-requirements.md](../product-requirements.md) のセカンダリーペルソナ（非エンジニアの合唱団員）が「説明書なしで最初の1曲を完了できる」ことを要件としている。内部値は上級者には有用だが、大多数には判断不能なノイズになる
  - 上級者向けの内部値は、画面ではなくログ／エクスポート側で担保する

### 6.2 音部記号の表示名

`ALTO` と `TENOR` はどちらもハ音記号であり、合唱団員が日常的に出会う記号ではないため、**線の位置まで書いて区別できるようにする**。

| 内部値          | 表示                                   |
| --------------- | -------------------------------------- |
| `TREBLE`        | ト音記号                               |
| `BASS`          | ヘ音記号                               |
| `ALTO`          | アルト記号（ハ音記号・第3線）          |
| `TENOR`         | テノール記号（ハ音記号・第4線）        |
| `TREBLE_DOWN_8` | オクターヴ下ト音記号（テノールで頻出） |
| `UNKNOWN`       | 読み取れませんでした                   |

線の位置は `clefTable.ts` の中線定義（ALTO の中線 = C4 → C4 は第3線、TENOR の中線 = A3 → C4 は第4線）と整合している。

### 6.3 並び順は楽譜順（上から下）に固定する

不一致件数の降順ソートは**採用しない**。合唱団員のメンタルモデルは「上に高い声部、下に低い声部」という視覚的な楽譜の並びであり、そこから外れると認知負荷が上がる。4.5 のとおり、楽譜順への固定は現状の「並び順の意味が曲によって変わる」問題も同時に解消する。

「不一致のある行を見つけやすくする」目的は、ソート以外の手段で達成する:

- 不一致のある行にバッジ／色を付ける
- 表の上のサマリ文を「⚠ が付いた行だけ確認すれば大丈夫です（N 件）」と、**どこを見ればよいかまで言い切る**形にする

### 6.4 食い違い件数に分母は出さない

「420 音中 3 音（0.7%）」のような分母は**表示しない**。理由:

1. **ユーザーが分母を持っている**。「ソプラノで 3 個の食い違い」と言われれば、合唱団員は自分のパートの全小節を思い浮かべられる。規模感はアプリが供給しなくてよい
2. **意思決定を変えない**。3 でも 8 でもユーザーの行動は「音部記号を確認する」で同じ。PRD の KPI（プロトタイプ実測「音高照合ミスマッチ 0/784音」）が示すとおり、健全なら 0 が正常値であり、0 でない時点で確認の動機は足りている
3. **むしろ誤誘導しうる**。音部記号の誤検出は件数の大小と危険度が比例しない。「0.7% なら無視でよい」と読ませてはいけない
4. `NoteEvent` は `staffIndex` を持たないため、グループ単位の分母を出すには `systems[]` からの逆引きが必要になる。上記 1〜3 より、その実装コストを払う理由がない

### 6.5 `UNKNOWN` は「未検査」という第3の状態として扱う

4.4 のとおり `UNKNOWN` の 0 件は「問題なし」ではないため、**「確認済み」「要確認」とは別の状態として表示し、確認が必要な件数にも算入する**。

判断の根拠: PRD の 2 つのペルソナは移動ドの習熟度こそ違うが、いずれも**「楽譜をちゃんと読みたい人」**である。音部記号を正しく読むことは両者に共通する関心事であり、「読み取れませんでした。何でしたか？」と尋ねるのは煩わしさではなく親切として受け取られると判断した。

ユーザーが正しい音部記号を選べば `corrections` が `staff.clefKind` を上書きし、**クロスチェックが実際に走るようになる**（`ScoreModelBuilder`）。つまり訂正には具体的な効果がある。

### 6.6 表示文字列の「正」はコードに置く

[CLAUDE.md](../../CLAUDE.md) の二重管理防止の方針に従い、次のように線を引く。

| 内容                                             | 正の置き場所                   | 理由                                               |
| ------------------------------------------------ | ------------------------------ | -------------------------------------------------- |
| 「なぜ『パート』と呼ぶか」等の方針・根拠         | **用語集**                     | 判断の記録であり、コードには書けない               |
| 「ト音記号」「ヘ音記号」等の音楽用語としての定義 | **用語集**                     | 実装の都合ではなく音楽の言葉そのもの               |
| UI に出す文字列そのもの                          | **コード**（表示名モジュール） | 文言は今後も磨く。用語集と二重管理すると必ずズレる |

4.7 の `G-clef-8vb` は、まさにこの線引きを怠った結果ズレた実例である。

## 8. 用語集への追記案

### 8.1 既存エントリ「システム（段）/ 譜表 / 小節」に「説明」を追加

このエントリは現状「定義」と「英語表記」しか持たず、他のエントリにある「説明」が欠けている。

```markdown
**説明**: UI ではシステムを一貫して「段」と表示する（練習現場の「2段目の4小節目から」
という言い方に合わせる）。「システム」という語は UI に出さない。
「譜表」も UI には出さず「パート」と表示する（→ パート）
```

### 8.2 新規エントリ「パート」（ドメイン用語セクション）

```markdown
### パート

**定義**: 1本の旋律線を担当する声部。合唱団員の日常語では
「同じ譜面上の1本の線を共有して歌う人の集団」を指す（例:「テノールパート」）

**説明**: MusicXML の `<part>` ＝ ScoreModel の `Part` に対応し、`partId`（P1, P2, …）で識別する。
v1 の対象である合唱の開離譜では「日常語のパート」「MusicXML の part」「譜表」の三者が一致する
ため、UI では一貫して「パート」と表示し、「譜表」という語は出さない。

一致が崩れる例（v1 ではスコープ外）:

- 賛美歌等の 2 段譜: 1 譜表に 2 パート（上段に S+A）
- ピアノ伴奏: 1 パートに 2 譜表（大譜表）
- divisi: 日常語の「テノール」が 1 譜表上の 2 声部を総称する

将来これらを扱う際、モデル側は `Part`（論理）と `StaffRef`（物理）を既に分けているため
破綻しないが、UI 用語はこの前提の見直しが必要になる。

**関連用語**: システム（段）/ 譜表 / 小節、SATB、確認項目（ConfirmationItem）

**英語表記**: part（コード内: `Part` / `partId`。物理的な五線は `StaffRef`）
```

### 8.3 「オクターブ下ト音記号」の英語表記を実装に合わせる

```markdown
**英語表記**: octave-down treble clef
```

### 8.4 「ステータス・状態」セクションに音部記号の確認状態を追加

| 状態     | 条件                                                       | 意味                                                                                                                                                                         |
| -------- | ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 確認済み | 検出値あり ＋ `mismatchCount` = 0                          | クロスチェックを行い、食い違いが無かった                                                                                                                                     |
| 要確認   | 検出値あり ＋ `mismatchCount` > 0                          | 音部記号を誤検出している可能性が高い                                                                                                                                         |
| 未検査   | 検出値が `UNKNOWN`（Audiveris が音部記号を記録しなかった） | **クロスチェック自体が行われていない**。`mismatchCount` が 0 でも「問題なし」を意味しない（`headStepOctave` は `clefKind` が `null` なら `null` を返し、検算をスキップする） |

### 8.5 「確認項目（ConfirmationItem）」の表現をそろえる

定義の「**譜表 1 段ではなく**、(パート, 検出音部記号) のグループ」は「譜表」と「段」が同居して読みにくい。語彙整理に合わせて表現を見直す。

## 10. 未決事項・今後の宿題

- **音部記号の切り抜き画像表示**: `ConfirmationItem` は既に `clipRect`（代表譜表の音部記号あたりの近似矩形）を持っている。元画像のその部分を小さく表示できれば、**名前を読まずに目で照合できる**。文字による説明は本来その代替にすぎない。ただし表示には PDF.js の導入が必要で、Editor のビューアと同時に入る想定（`confirmationItems.ts` のコメント参照）。本メモの施策はそれまでの間の解でもある
- **パート名のユーザー命名**: 「上から1番目のパート」ではなく、ユーザーが S/A/T/B を割り当てられるようにする案。認知負荷の低減効果は大きいが、「譜表」→「パート」の語彙置換だけで目的の大半が達成できると判断し、今回は見送る
- **2 段譜・ピアノ伴奏の扱い**: `docs/` のどこにも記述がなく、PRD のスコープ外リストにも挙がっていない未定義領域。5.1 の前提が崩れるのはこのケースなので、扱うと決めた時点で UI 用語を見直す
