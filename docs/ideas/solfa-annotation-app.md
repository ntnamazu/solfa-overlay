# アイデアメモ: 合唱楽譜への移動ド階名自動付与アプリ

- 記録日: 2026-07-12（同日、プロトタイプ検証まで完了）
- ステータス: プロトタイプ検証完了（PRD作成前）
- 発案者: Nobuhiro Takaichi

## 1. 一言で言うと

スキャンされた合唱楽譜のPDFを入力すると、全音符に移動ドの階名（および和音における役割）を自動で振り、印刷して使える注釈付きPDFを出力するアプリケーション。

## 2. 背景・課題

- 発案者は趣味で混声合唱をしており、相対音感を活かして楽譜を移動ドで読解・視唱している。
- 現状は、調号を前提に各音符の階名を解き明かし、Tonic sol-fa 略記（例: ファ→ "f"、シ♭→ "ta"）で音符の横に手書きメモしている。
- この作業は完全にルールベースの機械的作業でありながら、手書きのため多大な労力を要する。→ 自動化に適した課題。
- 移動ドによる楽曲理解は合唱演奏上有利とされることが多く、需要は発案者個人にとどまらない（階名唱の解説記事等で需要が確認できる）。

## 3. 入出力

| 項目 | 内容 |
|---|---|
| 入力 | 書店で購入した紙楽譜をスキャンしたPDF |
| 出力 | 元の楽譜に階名（＋和音役割）が付与された、印刷可能なPDF |

## 4. パイプライン構成（想定）

```
スキャンPDF
  → ① OMR: Audiveris （MusicXML ＋ .omr の2出力）
  → ② 解析: music21 （調検出・階名計算・和音解析）
  → ③ 出力: 元PDFへのオーバーレイ描画（.omr の記号座標 ＋ PyMuPDF 等）
```

- Audiveris は MusicXML とは別に `.omr` ファイル（段ごとのXMLを含むzip）を出力し、認識した各記号の元画像上のピクセル座標を持つ。解析は MusicXML、描画位置は `.omr` という二本立てが自然。
- 発案者は Audiveris の Docker 化・実行経験あり: https://github.com/ntnamazu/audiveris-docker

## 5. 要素技術の調査結果

- **OMR**: [Audiveris](https://audiveris.org/)（OSS、きれいな印刷譜で総合精度80〜90%程度）、深層学習系の oemer。商用では klang.io、PlayScore 2、ScanScore など。
- **音楽解析**: [music21](https://music21.org/)（MIT製 Python ライブラリ）。調検出、スケール度数算出（≒階名計算）、`chordify` による和音抽出、ローマ数字和声解析まで対応。
- **出力・再描画**: Verovio（MusicXML→SVG/PDF）、MuseScore CLI。ただし本アプリは再組版ではなくオーバーレイ方式を採る（後述）。
- **既存の部分解**: MuseScore には [movable Do で階名を歌詞として付与するプラグイン](https://musescore.org/en/project/add-solfa-names-lyrics-movable-do-la-or-do-based-minor-chromatic-alteration)が存在（La/Do基準の短調・半音変化に対応）。

## 6. 競合と差別化

### 競合状況

- 「PDF → Audiveris → MuseScore ＋ 階名プラグイン → PDF」という無料チェーンは手動で組める。これが事実上の最大の競合。ただし各ツールの習熟が必要で敷居が高く、出力は再組版された楽譜になる。
- 「階名の自動付与」を製品として提供するアプリは日本語圏・英語圏とも見当たらない。和音役割の表示まで含めると完全な空白地帯。

### 差別化ポイント

1. **元のPDFへのオーバーレイ**: 再組版ではなく、購入した楽譜の版面そのものに階名を重ね書きする。練習現場では「みんなと同じ版・同じページ割・練習番号」が死活的に重要であり、合唱者の実感に根ざした強い差別化。
2. **和音役割の表示**: 各音が和音の根音・第三音・第五音・第七音・第九音等のいずれかを注釈。根音はしっかり鳴らし、第三音は控えめに、という合唱の和音の鳴らし方（参考: https://hiradan.sub.jp/gasshokoza/cadenza.pdf ）を楽譜上に直接落とせる。競合不在。
3. **転調の扱いを人間と分担するUI**: 調号変更は自動検出できるが、調号が変わらない一時転調や読み替え点の位置は歌い手の解釈。「自動判定＋ユーザーが転調点と解釈先の調を指定・修正できるUI」とする。

## 7. 決定事項

| 論点 | 決定 | 補足 |
|---|---|---|
| 短調の読み方 | **La基準**をデフォルト | 発案者・所属合唱団ともLa基準。Do基準（主音を常にドと読み、me/le/te を使う）も設定で選択可に |
| 音節体系 | Tonic sol-fa 略記 / コダーイ式（di, me 等）を設定で切替 | 内部表現は「スケール度数＋変位」で持ち、表示時に文字列化する。2軸（音節体系×短調基準）は直交する設計 |
| 自動化の範囲 | 完全自動ではなく「自動＋人間が確認・修正するUI」 | OMR精度が80〜90%である以上、修正UIが体験設計の中心 |
| 和音役割レイヤー | 階名レイヤーとは独立に扱う | 和音役割は調にも階名設定にも依存しない安定した性質を持つ |
| 著作権対応 | 楽譜データをサーバーに一切保存しないローカル完結設計 | デスクトップアプリ、またはWASMによるブラウザ内ローカル処理。運用コストもほぼゼロになる副次効果 |
| リリース順序 | v1: 階名のみ → v2: 和音役割 | 理由は「8. リスク」参照 |

## 8. リスクと対策

### OMR精度（最大のリスク、ただし見立ては好転）

- 総合精度80〜90%には、本アプリが使わない情報（リズム・歌詞・強弱・スラー等）の誤認識が多く含まれる。階名付与に必要なのは音部記号・調号・臨時記号・音高のみで、**この用途に限った実効精度は総合精度より高い**。発案者の実験でも音名判定は良好だった。
- 誤りの被害は種類で二極化する:
  - 局所的誤り（臨時記号の見落とし等）→ 階名1音のずれ。発見も修正も容易。
  - 系統的誤り（音部記号・調号の誤認識）→ 段全体が全滅。特にテノールの「オクターブ下ト音記号」はOMRの鬼門。
- **対策**: 階名生成前に「検出された音部記号・調号の一覧」をユーザーに確認させる画面を挟む。1曲あたり数十個の確認で壊滅的エラーをほぼ全て捕捉できる。安く作れて効果が大きい、優先度の高いUI。

### 和音解析の本質的曖昧さ

- 経過音・掛留・倚音などの非和声音の判定は完全なルールベースでは解けない研究レベルの問題。music21 の chordify＋ローマ数字解析や AugmentedNet 等で「そこそこ」まで。
- 和音解析は音価（リズム）の認識精度に依存するため、階名レイヤーよりOMR品質への要求が厳しい。→ v2に後置。確信度が低い箇所は表示を控える／「?」を付ける誠実な設計とする。

### 転調検出の不完全さ

- 自動検出は不完全であることを前提に、UIでの指定・修正を一級の機能として設計する（差別化ポイントでもある）。

## 9. 用語整理（ブレストで確認した論点）

- **La基準 vs Do基準**: 短調の階名の振り方の流儀。イ短調の主和音 A–C–E を、La基準では「ラ・ド・ミ」（平行長調のドを維持。コダーイ／Tonic sol-fa の伝統）、Do基準では「ド・メ・ソ」（主音を常にド）と読む。この選択で短調パッセージの階名は全音変わる。
- **ローマ数字との関係**: ローマ数字は調の主音基準で振る慣習のため、階名の流儀（La/Do基準）とは連動しない独立した軸。
- **和音役割**: 根音・第三音・第五音等の判定は和音の内部構造だけで決まり、調にも階名設定にも依存しない。

## 10. プロトタイプ検証結果（2026-07-12 実施）

### 概要

Victoria《O magnum mysterium》（IMSLP #19716、Nancho Alvarez 版、パブリックドメイン、3ページ）を題材に、パイプライン全行程を実装・実行した。**「4. パイプライン構成」の設計がそのまま端から端まで動くことを実証**。

- 題材の特性: SATB・調号♯1（La基準で do=G、主音Aは「l」）・ムジカ・フィクタの臨時記号多数・テノールはオクターブ下ト音記号・左端に原典記譜のインチピット小譜表あり
- 成果物: `tmp/solfa-proto/` — `solfa_proto.py`（解析・階名計算）、`overlay_pdf.py`（PDF合成）、`annotations.json`（注釈レイヤーの中間データ）、`O_Magnum_Mysterium_solfa.pdf`（完成品）
- デモ（画像＋オーバーレイの検証ページ）: https://claude.ai/code/artifact/68dc56cd-465f-4c23-8e88-003faf07c22f

### 定量結果

| 指標 | 結果 |
|---|---|
| 階名を付与した音符 | 784音（幹音=赤、半音変化=紫で符頭上に配置） |
| 音高の照合ミスマッチ | **0 / 784**（.omr の譜表位置＋音部記号から逆算した音名 × MusicXML の音名） |
| 音符数不一致でスキップした小節 | 5小節 / 約296パート小節（階名欠落として残存） |
| 半音変化の階名 | de=31, ta=24, fe=10, se=3（G♯, F♮, C♯, D♯。Tonic sol-fa 規則どおり） |

### 仮説の検証

- **「音高認識の実効精度は総合精度より高い」→ 裏付けられた**。音高照合ミスマッチ0。リズム・歌詞等の誤認識は階名レイヤーに影響しなかった。
- **「系統的誤りは構造の誤認識で起きる」→ 実際に発生**。1ページ目の第1システムがインチピットの影響で4本の独立譜表に分解され、別楽章として認識された（Audiveris の book.xml の movement 分割情報から機械的に復元できた）。確認UIの必要性を実地で確認。
- **「局所エラーは小さく閉じる」→ 確認**。小節単位で突き合わせる設計により、不一致は5小節に閉じ、他へ波及しなかった。

### 技術知見

- `.omr` の音符座標（300dpi画像ピクセル基準）はオーバーレイに十分な精度。ページのポイント座標へは線形スケールで変換できる
- 譜表→パートの対応は sheet XML の `part id`（= book.xml の logical-id）で取れる。Audiveris の符頭 pitch は「中線=0・下向き正」
- 解析部は **Python 標準ライブラリのみ**で実装できた（music21 は今回の範囲では不要。和音解析フェーズでは必要になる見込み）
- Audiveris は Docker なしでも .deb を展開し同梱JREでヘッドレス実行可能（`GDK_SCALE=1` と `-Djava.awt.headless=true` が必要）

### 発見された改善課題（PRDへの入力）

1. **階名の書体**: Helvetica の小文字「l」が縦棒にしか見えず視認性が低い。書体選定は製品品質に直結する
2. **配置の衝突回避**: 階名が臨時記号等と重なる箇所がある。周囲の空きを見て逃がす配置ロジックが必要
3. **スキップ小節の穴埋め**: 音符数不一致でスキップした小節は階名が欠落する。修正UIで人間が補う領域そのもの
