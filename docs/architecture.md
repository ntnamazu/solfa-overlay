## アーキテクチャパターン

### プロセス構成（Electron）

```
┌───────────────────────────────┐
│ Renderer プロセス（UIレイヤー）      │  画面表示・編集操作
│  - 取込/確認/Editor/出力画面        │  contextIsolation 有効
└──────────────┬────────────────┘
               │ 型付きIPC（contextBridge 経由）
┌──────────────┴────────────────┐
│ Main プロセス                     │
│ ┌───────────────────────────┐ │
│ │ 編成レイヤー                   │ │  IPCハンドラ / OmrRunner
│ │ （IPC受付・委譲・OMR実行制御）    │ │  下位2レイヤーへの委譲のみ
│ ├─────────────┬─────────────┤ │
│ │ サービスレイヤー  │ データレイヤー  │ │  ScoreModelBuilder / SolfaEngine
│ │ （ドメインロジック │ （ProjectStore:│ │  AnnotationManager / OverlayRenderer
│ │  ・純粋TS）     │  .solfaproj   │ │  ※ サービス⇔データ間の直接依存は
│ │               │  読み書き）    │ │     禁止（編成レイヤーが仲介）
│ └─────────────┴─────────────┘ │
│        │ 子プロセス（引数配列で起動）  │
└────────┼──────────────────────┘
┌────────┴──────────────────────┐
│ Audiveris（同梱JRE・ヘッドレス）     │  PDF → MusicXML + .omr + book.xml
└───────────────────────────────┘
```

#### UIレイヤー（Renderer）
- **責務**: 画面表示、ユーザー入力の受付とバリデーション、編集操作の発行
- **許可される操作**: preload で公開された型付きIPC API の呼び出しのみ
- **禁止される操作**: Node.js API・ファイルシステムへの直接アクセス（`nodeIntegration: false`）、ドメインロジックの実装

#### 編成レイヤー（Main / IPCハンドラ・OmrRunner）
- **責務**: IPCリクエストの受付、サービスレイヤー（計算）とデータレイヤー（永続化）への委譲と結果の受け渡し、OMR実行制御（Audiveris 子プロセスの起動・進捗通知・キャンセル）
- **許可される操作**: サービスレイヤー・データレイヤーの呼び出し、Electron API の利用
- **禁止される操作**: ドメインロジックの実装（委譲のみに徹する）

#### サービスレイヤー（Main / ドメイン）
- **責務**: 照合、階名計算、注釈管理、PDF合成というドメインロジック（Electron 非依存の純粋TS）
- **許可される操作**: 共通型定義・定数（shared）の参照のみ
- **禁止される操作**: UI・Electron API への依存、データレイヤーの呼び出し（ファイルアクセスが必要な処理は編成レイヤーがデータを渡す→SolfaEngine 等のコアを純粋TSに保ち、ユニットテスト容易性を担保）

#### データレイヤー（Main / 永続化）
- **責務**: .solfaproj（zip）の保存・読込・世代バックアップ、設定ファイルの管理、出力PDF（注釈付きPDF）の原子的書き出し
- **許可される操作**: ファイルシステムへのアクセス
- **禁止される操作**: ドメインロジックの実装、サービスレイヤーへの依存（呼び出される側に徹する）

### 依存方向

```
Renderer(UI) → IPC → 編成(IPCハンドラ) → サービス   (OK)
編成(IPCハンドラ) → データ                          (OK)
サービス → データ           (NG: 永続化は編成レイヤーが仲介する)
サービス → Renderer        (NG: 通知はイベント購読で逆流させない)
Renderer → ファイルシステム  (NG)
```

## データ永続化戦略

### ストレージ方式

| データ種別 | ストレージ | フォーマット | 理由 |
|-----------|----------|-------------|------|
| プロジェクト（元PDF・OMR成果物・注釈・転調指定・設定） | ユーザーが指定した場所の `.solfaproj` ファイル | zip（project.json ＋ source.pdf ＋ omr/） | 1曲=1ファイルで持ち運び・バックアップが直感的。楽譜由来データをこの中に閉じ込める（ローカル完結） |
| アプリ設定（デフォルト音節体系・色・フォント等） | OSの標準アプリデータディレクトリ | JSON | 楽譜由来データを含まないため分離してよい |
| OMR実行ログ | アプリデータディレクトリ `logs/` | テキスト（ローテーション） | 失敗時の診断用。楽譜画像そのものは含めない |

### スキーマバージョニング

- `project.json` はルートに `schemaVersion`（整数。v1 = `1`）を必ず持ち、Zod スキーマの検証対象に含める
- **後方互換（新アプリ→旧ファイル）**: 自分より小さい `schemaVersion` のファイルは、読込時にマイグレーションして開く。マイグレーション後の保存は現行版数で行う
- **前方互換（旧アプリ→新ファイル）**: 自分より大きい `schemaVersion` のファイルは開かず、「新しいバージョンのアプリで作成されたファイルです」という読込エラーとして安全に失敗させる（データを壊さない）
- v2 の拡張（和音役割レイヤー等）でフォーマットを変更する際は、版数の増分とマイグレーション実装をセットで行う

### バックアップ戦略

- **頻度**: 保存（自動保存含む）のたびに直前版を世代バックアップ
- **保存先**: `.solfaproj` と同ディレクトリの `<name>.solfaproj.bak1..3`
- **世代管理**: 最新3世代を保持（1プロジェクト数十MB想定のため上限を設ける）
- **復元方法**: アプリの「バックアップから開く」メニュー、または .bak を手動でリネームして開く
- **書き込みの原子性**: 一時ファイルへ書き出してからリネームすることで、保存中クラッシュによる破損を防ぐ

## パフォーマンス要件

### レスポンスタイム（PRD非機能要件の実現方針）

| 操作 | 目標時間 | 実現方針 |
|------|---------|---------|
| OMR〜階名〜出力の全処理（10ページ） | 10分以内 | 支配項はAudiveris。ページ単位進捗表示＋キャンセルで体感を担保 |
| 確認・修正UIの操作 | 1秒以内 | 注釈編集は差分更新。ページ単位の遅延レンダリング |
| 修正後のPDF再出力 | 30秒以内 | pdf-lib による追記描画のみ（再エンコードなし） |
| プロジェクト自動保存 | UI非ブロック | 編集操作のデバウンス（300ms）＋Main側で非同期書込 |

### リソース使用量

| リソース | 上限 | 理由 |
|---------|------|------|
| メモリ | ピーク2GB（OMR実行中、JVM含む） | Audiveris のJVMヒープ（-Xmx で制御）＋アプリ本体。一般的な8GB機で他作業と共存できる水準 |
| ディスク（アプリ本体） | 800MB以内 | Electron＋同梱JRE＋Audiveris の合計。インストール障壁を上げない |
| ディスク（1プロジェクト） | 100MB以内 | スキャンPDF＋OMR成果物＋注釈。50ページ規模を想定 |

## セキュリティアーキテクチャ

### データ保護（ローカル完結の担保）

- **ネットワーク不使用**: 楽譜由来データを外部送信するコードパスを持たない。Renderer には CSP（`default-src 'self'`）を適用し、外部リソース読込も遮断する
- **依存の検査**: ネットワークアクセスを行う依存ライブラリを追加しないことをコードレビュー観点に含める（開発ガイドラインに規定）
- **アクセス制御**: プロジェクトファイルはユーザー所有のパーミッションで作成する。アプリデータディレクトリは OS 標準の場所を使う

### 入力検証

- **プロジェクトファイル**: zip 展開時にパストラバーサル（`../` を含むエントリ名）を拒否。project.json は Zod スキーマで検証し、不正値は読込エラーとして安全に失敗させる
- **PDF**: PDF.js / pdf-lib のパース失敗を捕捉し、例外を UI エラーに変換（クラッシュさせない）
- **子プロセス**: Audiveris の起動は引数配列（`spawn`）のみ。シェル文字列連結を禁止

### Electron ハードニング

- `nodeIntegration: false` / `contextIsolation: true` / `sandbox: true`
- preload で公開する IPC API は最小限の型付き関数に限定
- `openExternal` 等でユーザー提供の URL を開かない

## スケーラビリティ設計

### データ増加への対応

- **想定データ量**: 50ページ・8パート・約5,000音符／1プロジェクト（PRDスケーラビリティ要件）
- **パフォーマンス劣化対策**: 注釈・音符はページ索引付きで保持し、表示中ページ±1のみレンダリング。階名再計算は影響 KeyRegion 範囲に限定
- **アーカイブ戦略**: プロジェクトは独立ファイルのため不要（ユーザーのファイル管理に委ねる）

### 機能拡張性

- **注釈レイヤーの拡張（v2: 和音役割）**: `Annotation.layer` の判別子追加で拡張。和音解析エンジンはサービスレイヤーに `ChordAnalyzer` として追加し、SolfaEngine と独立させる（PRDの決定事項: レイヤー独立）
- **音節体系の追加**: SolfaEngine の文字列化テーブルを追加するだけで対応（内部表現は度数＋変位で不変）
- **OMRエンジンの差し替え**: OmrRunner をインターフェース化し、Audiveris 以外（oemer 等）の将来検証を可能にしておく。ただし .omr 相当の座標出力が前提条件

## テスト戦略

### ユニットテスト
- **フレームワーク**: Vitest
- **対象**: SolfaEngine（度数・変位・文字列化の全組合せ）、ScoreModelBuilder（照合・構造復元）、座標変換、衝突回避、Zod スキーマ
- **カバレッジ目標**: サービスレイヤーのコアロジック 90%以上

### 統合テスト
- **方法**: パブリックドメイン楽譜（Victoria《O magnum mysterium》）の実 Audiveris 5.6.1 成果物を
  フィクスチャとして同梱し、パース→照合を回帰テスト化（実測値: matched 295小節・808音・
  クロスチェック不一致0・skipped 1小節。根拠は `tests/fixtures/victoria/README.md`）。
  数値は Audiveris バージョンに依存するため、更新時はフィクスチャ再生成と差分レビューを行う。
- **divisi 回帰**: SSAATTBB divisi 曲（PD・20ページ8パート）の実成果物も同梱し、
  BookStructureResolver による構造解決後の実測値（matched 1029小節・3500音・skipped 135・
  StructureIssue 6件）を固定する。残るクロスチェック不一致は音部記号の誤検出が主因で、
  ClefKeyConfirm での修正が前提（根拠は `tests/fixtures/divisi/README.md`）。
- **対象**: パース→照合パイプライン、プロジェクトファイルの保存→再読込の同一性（後者は後続フェーズ）
- **申し送り**: 本物の Audiveris 起動を伴う E2E はコンテナでは不可（Audiveris/JRE 非搭載）。ホスト
  実機での手動確認に委ねる。OmrRunner は spawn を DI 化し、子プロセス以外のロジックを単体テスト化。

### E2Eテスト
- **ツール**: Playwright（Electron ドライバ）
- **シナリオ**: 新規プロジェクト→確認画面→修正→出力の一連操作、音部記号修正時の再計算、転調指定と手動注釈の保全

## 技術的制約

### 環境要件
- **OS**: Windows 10以降 / macOS 13以降 / Linux（x64・主要ディストリビューション）
- **最小メモリ**: 8GB（OMR実行時のJVMを考慮）
- **必要ディスク容量**: 1GB（アプリ本体＋作業領域）
- **必要な外部依存**: なし（JRE・Audiveris を同梱。Javaのインストール不要）

### パフォーマンス制約
- OMR処理時間は Audiveris に律速され、アプリ側で短縮できない。進捗表示・キャンセル・部分結果の提供で体験を担保する
- Audiveris のヘッドレス実行には `-Djava.awt.headless=true`（および Linux では `GDK_SCALE=1`）が必要（プロトタイプで確認済み）

### セキュリティ制約
- 楽譜由来データの外部送信禁止（PRDの著作権対応方針。実装・レビュー・依存追加のすべてで遵守）
- 自動アップデート機構を将来導入する場合も、送信するのはバージョン情報のみとする

## 依存関係管理

| ライブラリ | 用途 | バージョン管理方針 |
|-----------|------|-------------------|
| electron | アプリ基盤 | マイナー固定（~）。メジャー更新は動作検証を伴う計画的作業 |
| audiveris（同梱バイナリ） | OMR | 完全固定。更新時は統合テストのフィクスチャ再生成と精度回帰確認を必須とする |
| pdf-lib / pdfjs-dist | PDF入出力 | ^（マイナー自動）。出力PDFのスナップショットテストで回帰検知 |
| fflate / zod | zip・検証 | ^（マイナー自動） |
| fast-xml-parser | MusicXML / .omr sheet XML / book.xml の解析（サービスレイヤー） | ^（マイナー自動）。全 transitive 依存に network/fs/child_process コードがないことを追加時に確認済み（楽譜由来データの外部送信禁止に抵触しない） |
| vitest / playwright / eslint | 開発ツール | ^。CIで検証 |

**方針**:
- `package-lock.json` をコミットし、CI・配布ビルドは `npm ci` で再現性を保証する
- 楽譜認識の挙動に影響する Audiveris の更新だけは、専用の回帰手順（検証済み題材での定量比較）を経る
