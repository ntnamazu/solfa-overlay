### タスクスキップが許可される唯一のケース

以下の技術的理由に該当する場合のみスキップ可能:

- 実装方針の変更により、機能自体が不要になった
- アーキテクチャ変更により、別の実装方法に置き換わった
- 依存関係の変更により、タスクが実行不可能になった

スキップ時は必ず理由を明記:

```markdown

```

### タスクが大きすぎる場合

- タスクを小さなサブタスクに分割
- 分割したサブタスクをこのファイルに追加
- サブタスクを1つずつ完了させる

### フェーズ1 で判明した追加事実（フェーズ2 以降の判断材料）

案 A 適用後も 1 テストあたり約 400ms の下駄が残る。原因は `loadOmr`（`src/main/ProjectSession.ts:585`）が
`importPdf` / `open` のたびに呼ぶ `assemblePageGeometry()`。

当初は「同じ `.omr` を複数回 zip 展開していること」が主因と見立てたが、**後の実測で誤りと判明した**。
10 回ループの平均は次のとおり。

| 処理                             | 1 回あたり |
| -------------------------------- | ---------- |
| `unzipEntries()`（zip 展開のみ） | 約 19ms    |
| `assembleArtifacts()`            | 約 392ms   |
| `assemblePageGeometry()`         | 約 348ms   |

zip 展開自体は 19ms と軽く、**コストのほぼ全部が XML パース**だった。真の原因は
`parseSheetXml`（`OmrSheetParser.ts:215`）と `parseSheetGeometry`（同 `289`）が
**同じシート XML に対してそれぞれ `parseXml(xml, 'sheet')` を呼び、ツリーを 2 回構築している**こと。

これはプロダクションコードであり、requirements.md で**スコープ外**と宣言した領域のため本タスクでは触らない。
結果として成功指標「全体 10 秒未満」は案 A・B だけでは到達不能。指標の扱いは振り返りに記録する。
別タスクとして **Issue #1** に起票済み（https://github.com/ntnamazu/solfa-overlay/issues/1）。

### 学んだこと

**技術的な学び**:

- **「遅いテスト」の原因は個別のテストではなく共通の下ごしらえにあることが多い**。`--reporter=verbose` で
  テストごとの所要時間を出すと、大半が同じくらい遅い＝共通の下駄という形で一目で分かる
- **純粋関数の結果をテストで使い回すのは安全だが、共有オブジェクトの凍結までがセット**。deep freeze は
  テスト間汚染の予防であると同時に、「解析側は成果物を読むだけ」であることの実行時の証明にもなる
  （実際、凍結したまま 49 テストが通ったことで破壊的変更がないと確認できた）
- **待機ヘルパーは「観測手段の重さ」が決定的**。同じ「保存されたか」の判定でも、再オープン（400ms 超）と
  `readdir`（ほぼ 0ms）では桁が違う。仕様（`ProjectStore.save` のバックアップローテーション）を読むと
  軽い観測点が見つかることがある
- **Vitest の `projects` はルート直下の `test` を継承しない**。`coverage` はルートで効くため紛らわしく、
  推測ではなく実挙動で確認すべき箇所だった
- `Object.freeze` は要素を持つ TypedArray に対して `TypeError` を投げるため、再帰凍結では除外が必要

**プロセス上の改善点**:

- **変更前のベースラインを最初に計測したことが最後まで効いた**。各フェーズの効果を数値で切り分けられ、
  「案 A で 36.8s→23.1s、案 B で該当テストが 2720ms→1318ms」と貢献度を個別に語れる状態になった
- **実装順（A → B → C）が正しかった**。案 C を最後に回したことで「案 A・B だけで既定 5000ms を
  約 3.8 倍下回る」ことを先に確認でき、タイムアウト延長が遅さを隠す設定ではないと示せた
- **意図的にプロダクションを壊して退行確認したのが有効だった**。高速化したテストが「常に成功するだけの
  空テスト」になっていないことを、実際の失敗で証明できた（確認後 `git diff src/` が空であることも確認）
- 未達の成功指標を「達成したことにしない・こっそり指標を書き換えない」で、理由とともに記録した

### 次回への改善提案

- **性能改善タスクでは、下駄の原因を 1 つに決め打ちせず、最初に候補を洗い出す**。今回は
  `assembleArtifacts` を潰した後に `loadOmr` が出てきた。計画段階でプロファイルを取っていれば
  成功指標をより現実的に設定できた
- **シート XML の二重パースは別タスクとして起票済み（Issue #1）**。テストだけでなく**本番の取り込み・
  オープンの体感速度**にも効く（1 回あたり約 350ms）。改善すればテスト全体も 10 秒未満に届く見込み
- **「重そうな処理」を実測せずに主因と決めつけない**。今回、zip 展開を主因と見立てて報告したが、
  実測では 19ms しかかかっておらず、真因は同じ XML の二重パースだった。10 回ループで各処理を
  個別に測るだけで切り分けられたので、性能の話をするときは**必ず数値を取ってから結論を出す**
- CI ログに出ている `actions/checkout@v4` / `actions/setup-node@v4` の Node.js 20 非推奨警告も
  別タスクとして対応する（今回はスコープ外と判断）
