# 設計書

## アーキテクチャ概要

プロダクションコードは変更しない。変更対象は**テストコードとテスト設定のみ**。

「同じ入力から同じ結果を作り直す重複計算」を排除し、「本当に必要な重い処理」は必要な回数だけ呼ぶ形に直す。そのうえで CI 環境の速度差を吸収する余裕を設定で持たせる。

```
【現状】
  FakeRunner.run()  ──呼ばれるたび──> assembleArtifacts(RAW) 400ms  × 49 回
  waitUntil(条件)   ──ポーリング毎──> ProjectSession.open()   400ms超 × N 回
  testTimeout       ── 未設定（Vitest 既定の 5000ms に暗黙依存）

【変更後】
  ARTIFACTS = assembleArtifacts(RAW)  ← モジュール読み込み時に 1 回だけ（deep freeze 済み）
  FakeRunner.run()  ──────────────> ARTIFACTS を返すだけ           0ms
  waitUntil(条件)   ──ポーリング毎──> readdir() で bak1 の出現を確認  ほぼ 0ms
                    ──成立後 1 回──> ProjectSession.open() で内容検証
  testTimeout       ── 明示（CI ランナーの速度差ぶんの余裕）
```

## コンポーネント設計

### 1. `FakeRunner`（`tests/unit/main/ProjectSession.test.ts`）

**責務**:

- Audiveris を起動せずに、実フィクスチャ由来の OMR 成果物を `ProjectSession` へ供給する
- 呼び出し回数（`calls`）とキャンセル（`canceled`）の記録

**実装の要点**:

- `assembleArtifacts(RAW)` の結果をモジュールスコープの定数 `ARTIFACTS` として 1 度だけ組み立てる
- 成立の根拠は 2 点。どちらも既存コードに明記されている:
  - `assembleArtifacts` は**副作用のない純粋関数**（`src/main/omr/omrArchive.ts:11`）＝ 同じ入力なら必ず同じ結果
  - 本テストの検証対象は**パイプラインの呼び出し順序とユーザー判断の保持**であり、`assembleArtifacts` の正しさは domain 側テストの責務（`tests/unit/main/ProjectSession.test.ts:16-21`）
- 共有により全テストが**同一オブジェクトを参照**するため、テスト間汚染のリスクが新たに生じる。これを設計で潰す（下記）
- `raw: RAW` は現状すでにモジュール定数を共有しているため、この点の性質は変わらない

**テスト間汚染への対策（deep freeze）**:

- `ARTIFACTS` を再帰的に `Object.freeze` する
- 目的は 2 つ:
  1. 万一プロダクション側が `artifacts` を破壊的に変更していた場合、**テストが失敗して即座に検出できる**（strict モードでは凍結オブジェクトへの代入が `TypeError` になる。本プロジェクトの TS は strict、ES モジュールは常に strict）
  2. 「読み取り専用で共有してよい」という前提を、コメントではなく**実行時の保証**として固定する
- 凍結にかかるコストは起動時 1 回のみ。仮に無視できないコストだった場合は計測のうえ判断する（下記「パフォーマンス考慮事項」）

### 2. 自動保存テストの `waitUntil`（`tests/unit/main/ProjectSession.test.ts`）

**責務**:

- 予約された自動保存が**実際にファイルへ書かれた**ことを、実時間に依存せず待つ

**実装の要点**:

- 待機条件を「`ProjectSession.open()` が成功して `keyRegionDecisions.length === 1` になる」から「**世代バックアップ `song.solfaproj.bak1` が出現する**」へ変える
- 根拠は `ProjectStore.save()` のバックアップローテーション仕様:
  - `save()` は書き込み前に `rotateBackups()` を呼ぶ（`src/storage/ProjectStore.ts:105`）
  - 本体が既に存在する場合、`<path> → <path>.bak1` へ退避される（`src/storage/backupRotation.ts:49-51`）
  - テストは事前に `auto.save(path)` で本体を作っているため、**次の保存（＝自動保存）が起きた瞬間に `bak1` が必ず現れる**
- この検知方法は既存テスト「保存先が未確定なら自動保存しない」「ファイルを開いただけでは保存しない（バックアップ世代を無駄に消費しない）」が採る `readdir` ベースの発想と一貫する
- 検証の強度は下げない。`bak1` の出現は「保存が起きた」ことしか示さないため、**成立後に `open()` を 1 回だけ呼び、`keyRegionDecisions` の内容を検証する**

### 3. `vitest.config.ts`

**責務**:

- テストのタイムアウト値を明示し、CI ランナーの速度差を吸収する

**実装の要点**:

- Vitest の `projects` は独立した設定として扱われるため、ルート直下の `test` に書いても各プロジェクトへ継承されない可能性がある。**node / renderer 双方の `test` に明示する**（実装時に実挙動を確認して確定する）
- 値は `15000`（15 秒）。根拠:
  - 案 A・B の適用後、最も遅いテストでも 1 秒台に収まる見込み
  - 15 秒は「正常なテストなら決して踏まない」一方で「CI ランナーが数倍遅くても耐える」水準
  - タイムアウトを無効化（`0`）はしない。無限に待つと**本物のデッドロックやハングを検出できなくなる**ため
- なぜ設定するのかをコメントで残す。「遅いテストを見逃すため」ではなく「**環境差ぶんの余裕**」であることを明記する

## データフロー

### 自動保存テストの検証フロー（変更後）

```
1. auto.importPdf(pdfPath)            … ARTIFACTS を即座に受け取る（assemble しない）
2. auto.save(path)                    … 本体 song.solfaproj ができる（bak なし）
3. auto.setKeyRegionDecisions([...])  … 5ms 後の自動保存が予約される
4. waitUntil(readdir に bak1 が出現)   … 軽量ポーリング（最大 100 回 × 20ms）
     └ 自動保存が走る → rotateBackups が本体を bak1 へ退避 → 新しい本体を書く
5. expect(saved).toBe(true)           … 自動保存が起きたことの確認
6. reopened.open(path) を 1 回だけ     … 保存内容の確認（keyRegionDecisions が 1 件）
```

## エラーハンドリング戦略

### カスタムエラークラス

追加しない。

### エラーハンドリングパターン

- `waitUntil` が 100 回粘っても条件を満たさない場合は `false` を返し、`expect(saved).toBe(true)` で明示的に失敗する（現行の挙動を維持）。タイムアウトによる不親切な失敗ではなく、**アサーション失敗として読める**形を保つ

## テスト戦略

本タスク自体がテストの修正であるため、「変更後のテストが正しく機能すること」を以下で担保する。

### ユニットテスト

- `tests/unit/main/ProjectSession.test.ts` の 49 テストが**すべて通る**こと（テストの削除・スキップ・アサーション削減をしない）
- deep freeze により、プロダクション側が `artifacts` を書き換えていないことが実行時に保証される

### 統合テスト

- `npm run test` 全体（node / renderer 両プロジェクト）が通ること

### 退行防止の確認

- 変更前後で**テスト件数が変わらない**ことを確認する（高速化と引き換えに検証を削っていないことの証拠）
- 案 B の変更が「常に成功するだけの空テスト」になっていないことを、**意図的に自動保存を壊した状態でテストが失敗する**ことで確認する（確認後に元へ戻す）

## 実装の順序

1. **案 A**: `ARTIFACTS` 定数化 + deep freeze → テスト実行して全体時間を計測
2. **案 B**: `waitUntil` の条件を `bak1` 検知へ変更 + 検証を 1 回の `open()` に集約 → 該当テストの時間を計測
3. **案 C**: `vitest.config.ts` に `testTimeout` を明示 → 両プロジェクトへ効くことを確認
4. 退行防止の確認（テスト件数の一致、意図的な破壊での失敗確認）
5. 品質チェック（test / lint / typecheck / build）

案 A → B の順にするのは、A の効果で B の計測がしやすくなるため。C を最後にするのは、**A・B だけで既定の 5000ms を余裕で下回ることを先に確認**し、C が「遅さを隠す設定」になっていないことを保証するため。

## セキュリティ考慮事項

- 特になし。テストコードとテスト設定のみの変更で、配布物・実行時の権限・外部入力の扱いに影響しない

## パフォーマンス考慮事項

- deep freeze のコストは起動時 1 回。`OmrArtifacts` はページ・音符を含むオブジェクトグラフのため、再帰凍結が無視できないコストになる可能性がある。実装時に計測し、**凍結コストが節約分を食い潰す場合は凍結の範囲を見直す**（その場合も判断の根拠を tasklist に記録する）
- 案 C のタイムアウト延長は、**テストが遅くなることを許容する意味ではない**。成功指標（全体 10 秒未満）を満たしたうえでの保険として入れる

## 将来の拡張性

- 重いフィクスチャを使う他のテストファイルでも、同じ「純粋関数の結果をモジュールスコープで 1 度だけ組み立てる」パターンが使える
- テストが遅くなったときの調査手順（`--reporter=verbose` でテストごとの所要時間を出し、共通の下駄を特定する）は今回の振り返りに記録し、次回に活かす
