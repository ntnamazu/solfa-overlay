# 設計書

## 方針

文言の**書き換えそのものは小さい**（5 箇所）。この作業の主眼は、書き換えの根拠を
`docs/development-guidelines.md` に定着させ、**次に画面を足すときに同じ判断が再現できる状態**にすることにある。

したがって作業は次の 3 層で構成する。

```
docs/development-guidelines.md   ← 判断基準（なぜそう書くか）を新設
        │ 参照
        ├── src/renderer/screens/*.tsx        ← 実際の文言を是正
        └── docs/functional-design.md         ← 区画名を実装に追随させる
```

## コンポーネント設計

### 1. `docs/development-guidelines.md`（新設節）

**責務**:

- UI に出す日本語をどう書くかの判断基準を示す
- 各ルールに**根拠**（なぜそう書くか）と**外部出典**を添える

**実装の要点**:

- 追加位置は「コーディング規約」内、`### エラーハンドリング` の直後・`### セキュリティ規約` の直前。
  命名規則 → コメント規約 → エラーハンドリング と続く「書き方の規約」の並びに収める
- 既存節の書式（✅ 良い例 / ❌ 悪い例のコードブロック＋**原則**の箇条書き）に揃える
- 「内部識別子を画面に出さない」は機能設計書「画面に出す語彙の方針」に既にある。
  **本文を複製せず参照にとどめる**（二重管理の回避。先行作業で用語集とのズレが実際に起きている）

**追加する本文（案）**:

````markdown
### UIテキスト規約

画面に出す日本語は、**ユーザーを案内する**ために書く。丁寧さを積み上げるほど文は長くなり、
「何をすればよいか」が後ろへ追いやられる。

#### 指示は「〜してください」で書く

```typescript
// ✅ 良い例
'段の小節数を楽譜と見比べて入力してください';
'楽譜を見て選ぶと、そこから照合できるようになります';

// ❌ 悪い例
'段の小節数を楽譜と見比べて入力していただきたい';
'楽譜を見て選んでいただくと、そこから照合できるようになります';
```

「〜していただく」は「〜してもらう」の謙譲語であり、**隠れ主語がアプリ側**になる。
確認画面の作業はユーザー自身の楽譜を仕上げるための行動であって、アプリが恩恵を受ける構図ではない。
願望を重ねた「〜していただきたい」は、案内ではなく申し入れとして読まれる。

#### 見出しは名詞句にする

```typescript
// ✅ 良い例
<h2>直すところ（{n} 件）</h2>

// ❌ 悪い例
<h2>直していただきたいところ（{n} 件）</h2>
```

#### ユーザーが取る行動を書く。評価・感想は書かない

```typescript
// ✅ 良い例
'段の小節数がずれると、そのあとのページ全体に影響します。ここは直してから次へ進んでください';

// ❌ 悪い例
'段の小節数がずれると、そのあとのページ全体に影響します。ここだけは直しておく価値があります';
```

#### エラーは非難せず、次の一手を示す

読み取り結果が期待どおりでないことは**このアプリでは通常運転**である（OMR の限界）。
ユーザーの操作ミスとして書かない。

#### 敬語を使うのは、ユーザーが本来やりたくない操作を強いるときに限る

このアプリの確認画面は、ユーザー自身の目的（正しい階名付き楽譜を得る）に沿った作業なので該当しない。

#### 内部識別子・専門用語を画面に出さない

方針と実例は[機能設計書](functional-design.md)「画面に出す語彙の方針」を正とする。
表示文字列の実体は `src/renderer/labels/scoreLabels.ts` に置く（用語集と二重管理しない）。

**原則**:

- 指示は「〜してください」。「〜いただく」「〜いただきたい」は使わない
- 見出しに依頼表現を入れない
- 「〜することができます」ではなく「〜できます」
- 同じ概念を複数の言い回しで説明しない

**参考にした外部ガイドライン**:

- [SmartHR Design System「基本的な考え方」](https://smarthr.design/products/contents/writing-style/) — 「敬語を使いすぎない」「冗長な日本語を避ける」
- [Ubie Vitals「UXライティング ガイドライン」](https://vitals.ubie.life/ux-writing/) — UI コンポーネントでは原則として敬語を使わない
- [Apple HIG「Writing」](https://developer.apple.com/design/human-interface-guidelines/writing) — エラーメッセージで "we" を主語に立てない
- [Microsoft Writing Style Guide「Writing tips」](https://learn.microsoft.com/en-us/style-guide/global-communications/writing-tips) — 手順は命令法で書く
````

### 2. `src/renderer/screens/StructureConfirm/StructureConfirm.tsx`

**責務**: 楽譜の構成の確認画面。訂正できる項目と報告のみの項目を分けて提示する。

**実装の要点**:

- 4 箇所（`:125` / `:126` / `:130` / `:136`）の文言のみを変更する。**ロジックには触れない**
- `:125` は 1 文が長く、逆接（「〜ませんが」）で 2 つの情報を繋いでいる。
  「入力して直すところはありません。」で言い切ってから理由を続ける 2 文構成にする
  （Microsoft "Write short, simple sentences." に沿う）
- 見出し `:130` を「直すところ」に変えると、直下の 0 件時メッセージ（`:132`
  「読み取った構成に、直す必要のあるところは見つかりませんでした。」）と語が揃う

### 3. `src/renderer/screens/ClefKeyConfirm/ClefKeyConfirm.tsx`

**責務**: 音部記号と調の確認画面。

**実装の要点**:

- `:170` の「選んでいただくと」→「選ぶと」のみ。条件節なので敬語を落としても丁寧さは損なわれない
- 同ファイル `:178`「短調の曲は指定してください」は既に規約に沿っているため変更しない

### 4. `docs/functional-design.md`

**責務**: 画面仕様の記述。

**実装の要点**:

- 840 行目（区画表）と 852 行目（操作フロー）の「直していただきたいところ」を「直すところ」にする
- 「画面に出す語彙の方針」に、文言の書き方は開発ガイドラインを正とする旨の参照を 1 行足す

## データフロー

このタスクは表示文字列の変更のみで、状態遷移・IPC・永続化に影響しない。

## テストへの影響

現状、是正対象の文言を参照しているテストは 1 箇所のみ。

```
tests/unit/renderer/StructureConfirm.test.tsx:204
  expect(screen.getByRole('heading', { name: '直していただきたいところ（1 件）' }))
```

**実装時の確認事項**: 上記は `grep` で完全一致した 1 件だが、`getByText` の部分一致や
正規表現マッチで他の文言に依存しているテストが無いか、`StructureConfirm.test.tsx` と
`ClefKeyConfirm.test.tsx` を実際に読んで確認する（grep だけで判断しない）。

新規テストは追加しない。文言の是正であり、**検証している振る舞いは変わらない**ため、
既存テストの期待値を追随させるのが正しい（文言スナップショットテストの導入はスコープ外）。

## 実装の順序

1. `docs/development-guidelines.md` に「UIテキスト規約」を追加（＝判断基準を先に確定させる）
2. `StructureConfirm.tsx` の 4 箇所を規約に沿って是正
3. `ClefKeyConfirm.tsx` の 1 箇所を是正
4. テストの期待値を追随させる
5. `docs/functional-design.md` の区画名を追随させる
6. 品質チェック（test / lint / typecheck / build）

規約を先に書くことで、2〜3 の書き換えが「その場の語感」ではなく規約の適用になる。

## 検討したが採らなかった案

| 案                                               | 不採用の理由                                                                                                                                                              |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 「〜しましょう」に統一する                       | 勧誘形は動作主体が「アプリとユーザー」の両方に読め、曖昧になる。UI コンポーネントで敬語を使わない方針（Ubie Vitals）とも整合しない                                        |
| 見出しを「要確認項目」など漢語にする             | 先行コミットで決めた「合唱団員の語彙へ寄せる」方針に逆行する。SmartHR の「カタカナ語・専門語より平易な語」の考え方にも反する。和語の「直すところ」を維持する              |
| 画面の説明文もすべて `scoreLabels.ts` に集約する | `scoreLabels.ts` は**楽譜由来の値（音部記号・パート等）を表示名に変換する**モジュール。画面ごとの説明文まで持たせると責務が混ざり、どちらの理由で変更したのか追えなくなる |
| 文言スナップショットテストを入れる               | 文言は今後も磨く前提であり、スナップショットは変更のたびに落ちるだけで品質を守らない。規約をドキュメントに置く方が有効                                                    |
