# 要求内容

## 概要

確認画面の UI 文言に残る過剰敬語（「〜していただく」系）と評価表現を、直接的な指示表現
（「〜してください」）へ是正する。あわせて UI テキストのライティング規約を
`docs/development-guidelines.md` に明文化し、今後追加する画面で判断がぶれないようにする。

## 背景

先行コミット `fe6a4d6`（feat(ui): 確認画面の表示文字を合唱団員の語彙へ寄せる）で、
確認画面の内部識別子（`P1` / `TREBLE` / `UNKNOWN`）を合唱団員の語彙へ翻訳した。
このとき導入した文言のうち 5 箇所が「〜していただきたい」「〜していただく」という
謙譲語＋願望の形になっており、ユーザーから次の指摘を受けた。

> UIの画面でのユーザーのガイドの表記としてはほとんど見られない。「直していただきたい」は
> ユーザーを導く（案内する）というよりは申し入れを迫っているような印象があり、
> ユーザーにとっては負荷になるかもしれない。

この指摘は文法的にも裏付けがある。

- 「〜していただく」は「〜してもらう」の**謙譲語**であり、隠れ主語がアプリ側になる。
  確認画面の作業は**ユーザー自身の楽譜を正しく仕上げるための行動**であって、
  アプリが恩恵を受ける構図ではない。視点がねじれている
- 「〜していただきたい」はさらに話し手（アプリ）の願望を重ねるため、案内ではなく
  申し入れとして読まれる
- 敬語の階層を増やすと文が長くなり、「何をすればよいか」が文の後ろへ追いやられる

加えて、本プロジェクトにはこれまで**UI 文言を書くときのルールがどのドキュメントにも無い**。
先行コミットでは「表示文字列の正はコード側に置く」（＝どこに置くか）は決めたが、
「どう書くか」は決めていないため、画面を追加するたびに判断がぶれる。

### 根拠とした外部ガイドライン（原文確認済み）

| 出典                                          | 該当する記述                                                                                                                                                                     |
| --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| SmartHR Design System「基本的な考え方」       | **「敬語を使いすぎない」**「敬語表現を多用して、情報が伝わりづらくならないように配慮しましょう」／ OK:「◯◯を確認してください」 NG:「◯◯をご確認いただけますようお願いいたします」 |
| SmartHR Design System 同上                    | 「冗長な日本語を避ける」「社内用語など、一般的でない言葉を使わない」                                                                                                             |
| Ubie Vitals「UXライティング ガイドライン」    | 「基本的にボタン、見出しなどのUIコンポーネントでは原則として敬語を使いません」「ユーザーが本来やりたくないのに、やらざるをえない操作が発生するときは敬語を使います」             |
| Apple Human Interface Guidelines「Writing」   | "Avoid 'we' entirely, especially in error messages, as it creates ambiguity." ／ エラーは非難せず解決策を示す（"Choose a password with at least 8 characters"）                  |
| Microsoft Writing Style Guide「Writing tips」 | "Use active voice and indicative mood most of the time. **Use imperative mood in procedures.**"                                                                                  |

Apple の「"we" を主語に立てるな」は、日本語の「〜していただく」問題と同じ構図である
（日本語では主語が省略されるため気づきにくいが、文法上はアプリ側を隠れ主語に立てている）。

**不採用にした出典**: デジタル庁デザインシステムβ版「スタイルガイド」は、
「デザインシステムとスタイルガイドの違い」「スタイルガイドの作成方法」を説明するガイダンスであり、
日本語の敬語ルールは扱っていない（原文確認済み・本件の根拠には使えない）。

## 実装対象の機能

### 1. UI 文言の是正

`src/` 全体を `いただ` / `ましょう` / `ご確認` / `お願い` / `することができ` / `価値があ` で
走査した結果、対象は次の 5 箇所（コード内コメントの「開いただけ」は無関係のため対象外）。

| 箇所                       | 現在                                                                           | 是正後                                                                                               |
| -------------------------- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| `StructureConfirm.tsx:130` | 直していただきたいところ（N 件）                                               | 直すところ（N 件）                                                                                   |
| `StructureConfirm.tsx:125` | 入力して直していただくところはありませんが、読み取りで気になった点があるので〜 | 入力して直すところはありません。読み取りで気になった点があるので、目を通してから次へ進んでください。 |
| `StructureConfirm.tsx:126` | 直していただくことはありません。そのまま次へ進んでください。                   | 直すところはありません。そのまま次へ進んでください。                                                 |
| `StructureConfirm.tsx:136` | 段の小節数がずれると〜。ここだけは直しておく価値があります                     | 段の小節数がずれると〜。ここは直してから次へ進んでください                                           |
| `ClefKeyConfirm.tsx:170`   | 楽譜を見て選んでいただくと、そこから照合できるようになります。                 | 楽譜を見て選ぶと、そこから照合できるようになります。                                                 |

`:136` は「いただく」ではないが、**ユーザーが取るべき行動ではなく評価を述べている**点で同種であり、
Apple HIG の「解決策に焦点を当てる」に反するため同時に是正する。

### 2. ライティング規約の明文化

`docs/development-guidelines.md`「コーディング規約」に **「UIテキスト規約」** 節を新設し、
次を明文化する。各項目には**なぜそう書くか**の根拠を併記する（このプロジェクトの既存ドキュメントの流儀）。

- 指示は「〜してください」で書く。「〜いただく」「〜いただきたい」は使わない
- 見出しは名詞句にする（依頼表現を入れない）
- ユーザーが取る行動を書く。評価・感想は書かない
- エラーは非難せず、次の一手を示す
- 内部識別子・専門用語を画面に出さない（先行コミットで決めた既存方針をここへ集約）
- 敬語を使うのは、ユーザーが本来やりたくない操作を強いるときに限る

### 3. 機能設計書の追随

`docs/functional-design.md` の区画名「直していただきたいところ」（840 行目・852 行目）を
実装の見出しに合わせる。

## 受け入れ条件

### UI 文言の是正

- [ ] `grep -rn "いただ" src/` の結果が、コード内コメントの「開いただけ」（`ProjectSession.ts`）のみになる
- [ ] `grep -rn "価値があ" src/` の結果が 0 件になる
- [ ] 上表の 5 箇所がすべて是正後の文言になっている
- [ ] `npm test` / `npm run lint` / `npm run typecheck` / `npm run build` がすべてパスする

### ライティング規約の明文化

- [ ] `docs/development-guidelines.md` に「UIテキスト規約」節がある
- [ ] 各項目に ✅/❌ の具体例がある（既存のコーディング規約の書式に合わせる）
- [ ] 根拠にした外部ガイドラインの出典 URL が記載されている
- [ ] 「内部識別子を出さない」の既存方針が機能設計書と矛盾しない形で参照されている

### 機能設計書の追随

- [ ] `docs/functional-design.md` に「直していただきたいところ」の記述が残っていない
- [ ] 実装の見出し文言と機能設計書の区画名が一致している

## 成功指標

- UI に出る指示文が「〜してください」に統一され、謙譲語による依頼形が 0 件になる
- 次に画面を追加する担当者が、`docs/development-guidelines.md` だけを読んで
  同じ品質の文言を書ける状態になる

## スコープ外

以下はこのフェーズでは実施しない:

- 5 箇所以外の文言の全面的な見直し（今回の走査で過剰敬語は他に検出されていない）
- ボタンラベル・エラーメッセージ全体のトーン統一（別途、実機を触りながら判断する）
- 用語集（`docs/glossary.md`）の変更（表示文字列の正はコード側という既存方針を維持する）
- 文言のテスト用ヘルパー化・文言スナップショットテストの導入
