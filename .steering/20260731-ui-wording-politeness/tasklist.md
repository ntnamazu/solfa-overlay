### タスクスキップが許可される唯一のケース

以下の技術的理由に該当する場合のみスキップ可能:

- 実装方針の変更により、機能自体が不要になった

- 依存関係の変更により、タスクが実行不可能になった

スキップ時は必ず理由を明記:

```markdown

```

### 計画と実績の差分

**計画と異なった点**:

- **テストの依存が計画時の見積り（1 箇所）より 1 件多かった**。
  `StructureConfirm.test.tsx:155` の `toContain('目を通してから進んでください')` は、
  是正後の「目を通してから**次へ**進んでください」に部分一致しなくなる。
  grep の完全一致では検出できず、design.md に「テストファイルを実際に読んで確認する
  （grep だけで判断しない）」と書いていたため捕捉できた
- 規約の**原則**に「1 文を短くする。逆接で 2 つの情報を繋がず、言い切ってから理由を続ける」を
  追加した（design.md の案には無かった）。`:125` を 2 文構成にした判断の根拠が
  規約側に無いと、次に同じ判断ができないため

**新たに必要になったタスク**:

- ステアリングファイルの Prettier 整形（md の表が桁揃えされていなかった）

**技術的理由でスキップしたタスク**: なし（全タスク完了）

### 学んだこと

**技術的な学び**:

- **文言変更のテスト影響は grep の完全一致だけでは足りない**。
  Testing Library の `toContain` は部分一致なので、**文を伸ばす方向の変更**
  （「進んで」→「次へ進んで」）で壊れる。逆に**縮める方向の変更**は通ってしまい、
  テストが実質的に何も守らなくなる。どちらも grep では見えない
- 文言の是正は「振る舞いは変わらない」変更なので、新規テストは追加せず
  既存テストの期待値を追随させるのが正しい。文言スナップショットは
  変更のたびに落ちるだけで品質を守らないため入れなかった

**プロセス上の改善点**:

- **規約を先に書いてから文言を直す順序**にしたことで、5 箇所の書き換えが
  「その場の語感」ではなく規約の適用になった。後から規約を書くと、
  書いた文言を追認するだけの文書になっていたはず
- design.md に「検討したが採らなかった案」を**実装前に**書いておくと、
  実装中に選択肢を再検討せずに済む（今回は「〜しましょう」「要確認項目」を事前に却下済み）
- ユーザーの違和感の指摘に対し、**外部の公開ガイドラインで裏を取ってから**着手した。
  SmartHR Design System「敬語を使いすぎない」の OK/NG 例が指摘と一致していたため、
  好みの問題ではなく再現可能な基準として規約化できた

### 次回への改善提案

- UI 文言を変えるときは、対象文言の**一部を含む**テストが無いか必ずテストファイルを読む。
  `grep` は「変更前の文字列そのもの」しか見つけられない
- ボタンラベル・エラーメッセージ全体のトーン統一は、実機（`npm run dev`）を触りながら
  判断する。今回はスコープ外に置いた
- 規約に追記が必要になったら `docs/development-guidelines.md`「UIテキスト規約」へ集約する。
  機能設計書には「何を語彙として選ぶか」だけを書き、「どう書くか」は書かない
