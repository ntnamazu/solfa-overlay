# 要求内容

- 作業名: 20260719-phase4-confirm-flow-persistence（ロードマップ Phase 4: 確認フローと永続化）
- 対応機能要件: F-2（音部記号・調号の確認画面）／信頼性要件（修正作業の永続化）

## 概要

OMR 結果をユーザーが確認・訂正し、その判断をプロジェクトファイル（`.solfaproj`）に永続化する
フローを実装する。Phase 3 までで「UI なしで実データが階名まで通る」状態になったため、
本フェーズで**それを GUI から操作できる状態**にし、同時に**ユーザーの訂正が失われない**ようにする。

## 背景

### 1. ClefKeyConfirm は「あると良い UI」ではなく必須要件に格上げされている

Phase 3 の着手前調査で、**Audiveris は `<key><fifths>` のみを出力し `<mode>` を書かない**ことが
判明した。長調/短調の自動判別が原理的に不可能で、自動生成される `KeyRegion` は全て長調になる。
その結果、**La 基準の移動ド（本アプリの主目的の1つ）が自動では一切効かない**。
ユーザーが調の長短を指定できる導線がなければ、この制約は永久に解消しない。

> **【実装後の訂正】この前提は不正確だった。** 実装検証で `SolfaEngine.resolveDo` を追ったところ、
> La 基準は短調の主音を La と数える＝ do を「主音の短3度上」＝**平行長調の主音**に置くため、
> 自動判定の「常に長調（＝平行長調）」のままでも **La 基準の階名は既に正しい**ことが分かった。
> 旋法の指定が階名に効くのは **Do 基準のとき**である。
> ただし調区間の表示（「イ短調」と出るか「ハ長調」と出るか）と v2 の和音役割分析はどちらの基準でも
> 旋法を要求するため、**ClefKeyConfirm で旋法を指定できるようにすること自体は引き続き必要**であり、
> 本フェーズの成果物は無駄になっていない。詳細は `docs/functional-design.md` の
> 「KeyRegionBuilder / 実データの制約」を参照。

### 2. 着手前の実データ計測（本作業で実施）が設計の主要分岐を確定させた

Phase 2・3 で 2 回連続で有効だった「着手前に実データの分布を出す」を今回も実施し、
`tmp/probe`（作業後に削除）で以下を実測した。**この 2 点が UI 設計とテスト設計を決めた**。

**計測1: 音部記号を訂正するとクロスチェック不一致がどれだけ減るか**

| 指標                           | 訂正前 | ALTO→TREBLE 訂正後 |
| ------------------------------ | ------ | ------------------ |
| `pitchCrossCheckMismatch` 合計 | 569    | **111**            |
| P6（35 段が ALTO 誤検出）      | 402    | **0**              |
| P4                             | 38     | **0**              |
| P7                             | 119    | 101                |
| P8                             | 10     | 10                 |

Phase 2・3 から申し送られていた「音部記号の誤検出が主因」という推定が**定量的に裏付けられた**。
訂正対象は ALTO と検出された 41 譜表のみで、80% の不一致が解消する。
**この数値がそのまま本フェーズの回帰テストの期待値になる。**

**計測2: 確認画面に何行並ぶか（「1曲5分以内」の受け入れ条件に直結）**

| 指標                            | Victoria | divisi  |
| ------------------------------- | -------- | ------- |
| 譜表数（page × system × staff） | 36       | **288** |
| (partId, clefKind) の異なり数   | 5        | **17**  |

譜表を 1 行ずつ並べると divisi は **288 行**で、5 分以内の目視照合は不可能。
一方 **パート×検出音部記号でグルーピングすると 17 行**に畳める（P6 は「ALTO 35 段」が 1 行）。
**確認単位をパート×検出値のグループにする**という設計判断は、この計測がなければ出せなかった。

### 3. 訂正が永続化されないと確認作業が毎回やり直しになる

現状プロジェクトの保存手段がなく、OMR は 10 ページで数分かかる。
確認画面での判断（`ConfirmationItem.corrected` / `StructureDecision` / 調の長短）が
セッション限りで消えると、実用に耐えない。

## 実装対象の機能

### 1. 確認項目の生成（domain）

- `buildConfirmationItems()`: 確定構造と照合結果から、**パート×検出音部記号でグルーピングした**
  確認項目を生成する
- クロスチェック不一致の件数をグループごとに集計し、**不一致の多い順に並べる**
  （機能設計書「警告表示: 不一致のある譜表を強調し一覧の先頭に出す」の実装）
- 1 グループの訂正が、そのグループに属する全譜表へ一括で適用される

### 2. 調文脈のユーザー訂正（domain）

- `KeyRegionDecision`（調文脈ごとの調号 `fifths` ／旋法 `mode` の上書き）を新設
- `KeyRegionBuilder.build()` が decisions を受け取り、訂正を反映した `KeyRegion[]` を返す
- 訂正の結果、隣接する区間が同じ調になったら**マージする**
  （Phase 3 のコードレビュー修正1と同じ「存在しない転調点を描く」defect の再発防止）
- **これにより Do 基準の移動ドが初めて正しく機能し、調区間の表示も実態に合う**
  （当初は「La 基準が初めて機能する」と書いていたが、上記の訂正のとおり誤り）

### 3. プロジェクトの永続化（storage）

- `.solfaproj`（zip: `project.json` ＋ `source.pdf` ＋ `omr/`）の保存・読込
- `project.json` の Zod スキーマ検証と `schemaVersion` の前方/後方互換
- 原子的書き込み（一時ファイル → リネーム）と `.bak1..3` の世代バックアップ
- OMR 成果物の同梱により、**再開時に OMR を再実行しない**

### 4. IPC 編成レイヤー（main）

- OMR 実行・進捗通知・キャンセル、構造解決、照合、調文脈生成、階名計算を Renderer へ公開
- プロジェクトの新規作成・保存・読込
- Main 側にセッション状態を持ち、**Renderer は状態を持たない**（アーキテクチャ設計書の依存方向）

### 5. 画面（renderer）

- **Home**: PDF を開く／既存プロジェクトを開く
- **OmrProgress**: 進捗表示とキャンセル
- **StructureConfirm**: `StructureIssue` の一覧と段の小節数の上書き
- **ClefKeyConfirm**: 音部記号グループ表＋調文脈表（調号・長短の指定）、承認で `completedAt` を確定

## スコープ外

以下はこのフェーズでは実装しません:

- **`clipRect` の切り抜き画像表示**: 元 PDF のページ画像化には PDF.js の導入が必要で、これは
  Editor 画面のビューア（Phase 5）と同時に入れるのが妥当。本フェーズでは `clipRect` の**値**を
  符頭座標から近似して持たせるに留め、画面には検出値・対象段数・不一致件数をテキスト表示する
- **`PageInfo` の実値**: PDF のポイント寸法の取得には pdf-lib / PDF.js が必要（Phase 5）。
  スキーマ上のフィールドは定義し、本フェーズでは空配列を永続化する
- **Editor / Export 画面**: Phase 5（F-4 注釈付き PDF 出力）の担当
- **AnnotationManager / OverlayRenderer**: Phase 5
- **転調点の新規追加 UI（F-6）**: Phase 6。本フェーズの `KeyRegionDecision` は
  **既存の自動検出区間の訂正のみ**を扱い、新規区間の挿入は行わない
- **Playwright による E2E**: GUI が Editor まで揃う Phase 5 以降。本フェーズは
  jsdom によるコンポーネントテストで代替する
- **譜表→パートの再割当**: MusicXML 側のパート再スライスが必要（記録済みの負債）

## 環境上の制約（申し送り）

本 devcontainer は **GUI を起動できない**ため、画面の見た目の確認はホスト実機での
`npm run dev` に委ねる。本フェーズでは jsdom + Testing Library によるコンポーネントテストで
描画・操作ロジックを自動検証し、視覚的な確認のみを手動 QA に残す。
