## 🚨 タスク完全完了の原則

**このファイルの全タスクが完了するまで作業を継続すること**

### 必須ルール

- **全てのタスクを`[x]`にすること**
- 「時間の都合により別タスクとして実施予定」は禁止
- 「実装が複雑すぎるため後回し」は禁止
- 未完了タスク（`[ ]`）を残したまま作業を終了しない

### 実装可能なタスクのみを計画

- 計画段階で「実装可能なタスク」のみをリストアップ
- 「将来やるかもしれないタスク」は含めない
- 「検討中のタスク」は含めない

### タスクスキップが許可される唯一のケース

以下の技術的理由に該当する場合のみスキップ可能:

- 実装方針の変更により、機能自体が不要になった
- アーキテクチャ変更により、別の実装方法に置き換わった
- 依存関係の変更により、タスクが実行不可能になった

スキップ時は必ず理由を明記:

```markdown
- [x] ~~タスク名~~（実装方針変更により不要: 具体的な技術的理由）
```

### タスクが大きすぎる場合

- タスクを小さなサブタスクに分割
- 分割したサブタスクをこのファイルに追加
- サブタスクを1つずつ完了させる

### 計画と実績の差分

**計画と異なった点**:

- **README の「実装状況」の更新が、想定より重い意味を持った**。計画時は「Phase 5 完了を反映してチェックを付ける」程度の認識だったが、実装コードを確認したところ**逆方向のズレ**も見つかった。`Editor.tsx` の実装コメントに「Phase 5 は**テキストによる最小表示**に留める。元PDF のページ画像に注釈を重ねるキャンバス表示（PDF.js）と、注釈の手動編集・転調点の指定は Phase 6（F-5 / F-6）の担当」と明記されており、README が謳う「Editor（注釈修正UI）」はまだ存在しなかった。さらに `DEFAULT_SETTINGS.ts` の `syllableSystem: 'kodaly'` は renderer 側に一切露出しておらず、階名表記の切り替えは画面から行えない。**完了した機能に `[x]` を付けるだけでなく、「まだできないこと」を能動的に書き足す**方針へ変更した。
- **`THIRD_PARTY_LICENSES.md` の修正箇所が1か所ではなかった**。計画では「71 行目以降の TODO 節を差し替える」としていたが、mere aggregation 節（41 行目）にも「アプリ本体自身のライセンスは下記 TODO」という参照が埋まっていた。TODO の語をファイルから消すという受け入れ条件を `grep` で検証したことで発見できた。
- **J-PlatPat の根拠 PDF 保全が実行不可能になった**。ユーザーが調査完了後に原本を削除したため。調査条件（サービス・検索方法・区分・実施日）をメモに残すことで**追試可能性**を担保する方針へ切り替えた。原本を保全するより、条件を残すほうが再現性の観点で優れている面もある。

**新たに必要になったタスク**:

- **README のリンク整合の機械的検証**。手作業では見落とすため、`grep` でローカルパス参照（相対リンク・`<img src>`）を抽出し、`[ -e ]` で実在を確認するワンライナーを回した（12 件すべて実在）。README を全面書き換えする作業では必須の工程だった。
- **`docs/repository-structure.md` への画像素材ルールの明文化**。単に `assets/` を追記するだけでなく、「PD 素材のみ配置可・出典明記・配布物には含まれない」というルールを併記した。`tests/fixtures/` に既存の「テストデータの著作権ルール」があるのに、README 掲載素材には同等のルールが無いままだと、将来購入譜のスクリーンショットを置いてしまう余地が残るため。

### 学んだこと

**技術的な学び**:

- **SmartScreen 警告のトリガーは Mark of the Web（MOTW）**。ローカルでビルドした `.exe` を同じ PC で実行しても MOTW が付いていないため警告は出ない。「ビルドしたら警告が出なかった＝署名不要」という早合点を避けられた。配布前の検証は `Set-Content -Stream Zone.Identifier` で MOTW を手動付与して行う。
- **SmartScreen 警告画面の背景色は Windows のアクセントカラー設定に追従する**（実機検証済み）。「青い全画面」は既定のアクセントカラーが青系であることに由来する通説にすぎず、赤系にもなる。**変更を反映するにはOSの再起動が必要**だった（DWM がプロセス起動時に色を読み込むためと推測される）。README で色を断定すると、赤い警告を見た利用者に「別のもっと危険な警告では？」という不安を与える。
- **AGPL 同梱物と MIT 本体の関係は「本体のライセンスを書くだけ」では不十分**。「本体が MIT」という記述だけを読んだ再配布者が「配布物全体が MIT」と誤読しうる。構成要素ごとのライセンス一覧表と、**再配布時に同梱 Audiveris 部分へ AGPL-3.0 の条件が及ぶ**という明示的な注意書きの両方が要る。
- **SemVer のメジャー 0 は「まだ固まっていない」を版数だけで宣言できる札**。UI に既知の改善余地があり破壊的変更を見込む段階で 1.0.0 を名乗ると、期待値と実物のギャップを自ら作ることになる。デスクトップアプリでは SemVer の「公開 API」を「利用者から見た UI と出力仕様」と読み替えるのが実用的。

**プロセス上の改善点**:

- **受け入れ条件を「`grep` で機械的に検証できる形」で書いたことが効いた**。「TODO の記述が残っていない」「『（仮称）』の記述が残っていない」といった条件は、最後にワンライナーで一括照合でき、`THIRD_PARTY_LICENSES.md` の隠れた TODO 参照の発見にもつながった。ドキュメント作業でも検証可能な受け入れ条件は書ける。
- **ユーザー操作が必要なタスク（GitHub のリポジトリ名変更）を tasklist に明示的に含めた**のが良かった。「ユーザー操作 → 完了報告後にローカル追従」とサブタスクに分解しておくことで、待ちの状態が可視化され、完了後の追従作業（`git remote set-url` と疎通確認）も漏れずに実施できた。
- **実装対象がコードでなくドキュメントでも、実装コードを読む工程は省けない**。README の「実装状況」を書くために `src/renderer/screens/` の構成、`Editor.tsx` の実装コメント、`DEFAULT_SETTINGS.ts` の既定値を確認した。ドキュメントだけを見て書いていたら、存在しない機能を「実装済み」と喧伝するところだった。

### 次回への改善提案

- **README の「実装状況」は、機能追加のたびに更新する運用にする**。今回は Phase 3 時点の記述が Phase 5 完了後も残っていた。各 steering の「フェーズ4: ドキュメント更新」に「README の実装状況を更新」を定型タスクとして入れると漏れにくい。
- **公開後に届くフィードバックの受け皿を決めておく**。README では Issues へ誘導したが、合唱仲間（非エンジニア）が GitHub アカウントを持っているとは限らない。利用者層に合わせた導線（口頭・メール等の集約方法）を次の作業で検討する。
- **Phase 6（注釈の手動編集・PDF プレビュー）の優先順位は、公開後のフィードバックを見てから決める**。現在の「テキスト一覧で確認して書き出す」形式が実用上どこまで許容されるかは、実際の利用者の反応でしか分からない。先回りして作り込まず、v0.1.0 の反応を待つ。
