## 実装後の振り返り

### 実装完了日

2026-10-11

### 計画と実績の差分

- **構成は design.md どおり**（型 → domain → storage → Main → Renderer → 統合テスト）。依存の追加なし
- **既存テストの修正が計画より広くなった**: `ScorePreviewPage` に小節の範囲（`measures`）を足したことで、段があるページは
  必ず重ね描きのページとして作られるようになった。「ページが無い」で「ほかの種類も無い」を確かめていた `scorePreview` の
  テストを、種類ごとに集めて確かめる形（`collect`）へ書き換えた
- **小節番号の思い込みを実測で訂正**: Victoria の自動の区切りを「通し 27」と見込んでテストを書いたが、実測は 28。テストは実測値に合わせた
- **implementation-validator の指摘**: 必須・推奨の指摘なし。提案 3 件のうち 2 件（`measureRegions` の縦範囲の前提、
  renderer のテストが domain を参照する理由）をコメントで反映。`panelKey` の切り出し（提案 1）は理解を妨げないため見送った
- **スコープの判断**: 拍位置からの転調は requirements.md のスコープ外とし、機能設計書の既知の限界に記録した。
  PRD F-6 の受け入れ条件は「小節・拍」のままのため、拍位置の要否は別途判断が要る

### 学んだこと

- **ユーザー判断と解析結果のキャッシュを分ける原則**がそのまま効いた。指定を `keyRegions` に直接書かず `keyChanges` に持ったため、
  再解析・保存→再読み込み・確認画面の訂正のいずれでも指定が生き残り、「編集直後の画面＝再読み込み後の画面」を `toEqual` 1 本で検証できた
- **同じ小節に 2 種類のユーザー判断が重なる**（確認画面の訂正と転調点の指定）ときは、適用順だけでなく「後からの操作を勝たせる」規則が要る。
  適用順（指定 → 訂正）は確認画面の表の都合で決まり、その裏返しとして Editor 側で同じ小節の訂正を外す必要があった
- **フィールドの追加は版数を上げる理由になる**: v0.3.0 が公開済みのため、旧アプリが未知のフィールドを黙って捨てる（Zod の既定）経路を
  v2 への版上げで塞いだ。スキーマの「足すだけなら版数据え置き」は、旧アプリで開いて保存されうるかどうかで判断する
- 主音表のように Main と Renderer の両方が要る**定数**は shared に置ける（関数は domain に残す）。表を 2 つ持つと「選んだ調と違う調で読まれる」

### 次回への改善提案

- 拍位置からの転調が必要なら、`NoteEvent` に単位をそろえた小節内位置（四分音符単位の分数など）を持たせるスキーマ変更から始める（`KeyChange` に `offset` を足す）
- 転調点の「元に戻す」（注釈削除の取り消しと同等）は未実装。削除は同じ調を選び直せば戻せるが、要望があれば `restore` 相当を足す
- この devcontainer の node_modules は Windows 向けに入っていることがある。テスト・ビルドには Linux 用の rollup / esbuild バイナリを
  スクラッチに入れて `NODE_PATH` と `ESBUILD_BINARY_PATH`（版ごとに振り分けるラッパー）で差し込んだ。リポジトリ側で手順化するかは要検討
- `ScoreViewer`「画面から離れたページは描画を止め、階名を外す」が全体実行で 1 度だけ失敗した（単体・再実行 2 回では成功）。
  既存のテストで今回の変更とは独立と見ているが、再発するなら ResizeObserver による描き直しとの競合を疑う

### 追記: コードレビュー（/code-review）への対応（2026-10-11）

**直したもの**:

- **#1（バグ）書き足した転調点を削除すると「適用できなかった指定」が残り続ける**: 削除を常に `remove` として保存していたため、
  自動判定の区切りが無い小節では取り除く区切りが無く、解析のたびに `unmatchedKeyChange` になっていた（保存されるため開き直しても消えない）。
  `KeyRegionBuilder` が自動判定の区切り（`detectedKeyRegions`）を返すようにし、`applyKeyChangeEdit` が「自動判定の区切りがある小節だけ `remove` を残し、
  無い小節は記録を消す」ように変えた
- **#2（仕様）上書きした自動判定の区切りを自動判定へ戻せない**: 編集に `revert`（自動判定に戻す）を足した（保存する `KeyChange` とは別の
  `KeyChangeEdit` 型）。「転調点を削除」は区切りごと取り除く、「自動判定に戻す（G 長調）」は指定を取り消す、と操作を分けた。
  削除した自動判定の区切りは楽譜の上から印が消えるため、「調の区切り」一覧に「削除済み」として残してそこから戻せるようにした
- **#3（#1 の副産物）** 編集の検証に使う小節数を、`score.systems` から求める独自計算をやめ、`KeyRegionBuilder` の範囲判定と同じ値（`measureCount`）にした
- **#4** 整数でない小節番号で「NaN 小節目」と出ないよう文言を分けた
- **#8** 保存ファイルの読み込みで、同じ小節の指定の重複を schema エラーにした
- **#6・#7** `scorePreview` の譜表の縦範囲（`stavesVerticalRange`）と矩形の座標変換（`toPreviewRect`）をスキップ小節の枠と小節の範囲で共有し、
  登録済みの小節では座標変換をしないようにした
- 見送り: #5（`setBusy(false)` を finally に入れる）は既存の App の操作すべてに共通する書き方で、IPC は失敗も `IpcResult` で返すため今回は扱わない

**学んだこと**:

- **「削除」の保存の形は、削除する前の状態の由来で変わる**。自動の区切りを消す操作は「消した」という記録が要るが、ユーザーが置いた区切りを消す操作は
  記録を消せばよい。ユーザー判断を記録として持つ設計では、取り消し・削除のたびに「記録を足すのか消すのか」を決める必要がある。
  F-5 の注釈（自動注釈は `deleted` の印、手動注釈は実体を消す）とまったく同じ構図で、最初の実装で踏襲しきれていなかった
- 削除と「元に戻す（自動判定へ）」は、上書きがある状態では結果が違う別の操作になる。最初から両方の操作を設計に入れておくべきだった
- 自分で書いたテストは「自分が想定した経路」しか通らない。書き足した転調点の削除という基本の往復をテストしていなかった。
  編集操作は「足す → 消す」「上書き → 消す／戻す」の往復を必ずテストに含める
