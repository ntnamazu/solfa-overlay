# 要求内容

## 概要

確認画面（StructureConfirm / ClefKeyConfirm）に露出している内部識別子と裸の数値を、合唱団員の語彙へ翻訳する。あわせて、表示が実態と食い違っている箇所（`UNKNOWN` の「食い違い 0 件」）を「未検査」という第 3 の状態として正しく表現する。

## 背景

壁打ちメモ [docs/ideas/ui-wording-improvement.md](../../docs/ideas/ui-wording-improvement.md)（2026-07-29 記録・方針決定済み）が本作業の入力である。実プロジェクト 4 件（`civabit-eos` / `o-quam-gloriosum` / `christus-factus-est` / `dolcissima-mia-vita`）の `project.json` を実測した結果、課題は次の 3 つに集約された。

| #   | 原因                                   | 該当箇所                                                            |
| --- | -------------------------------------- | ------------------------------------------------------------------- |
| ①   | 内部識別子がそのまま画面に出ている     | `P1`〜`P5`、`TREBLE`、`UNKNOWN`、`TREBLE_DOWN_8`                    |
| ②   | 数値に単位・文脈がない                 | 「音高の不一致 3」「対象の段数 10」「(1, 1, 1, 1, 4, 4)」           |
| ③   | その画面で何をすればよいか書いていない | 譜表構造の確認画面（全行が「—」になり操作の余地がない状態が起こる） |

さらに、単なる文言の問題ではない**実態との食い違い**が 2 件見つかっている。

1. **`UNKNOWN` の「不一致 0 件」は「問題なし」を意味しない**（メモ 4.4）。`UNKNOWN_CLEF` は Audiveris が音部記号を読み取れなかったことを表し、このとき `clefTable.headStepOctave` が `clefKind === null` で即 `null` を返すため**クロスチェック自体が走らない**。結果 `mismatchCount` は 0 のまま据え置かれ、「検算して問題なかった行」と画面上で区別できない。実害は階名の誤りではなく（音高は MusicXML 由来）、**「誤っていないことの保証が無い」**点にある
2. **並び順の意味が曲によって変わる**（メモ 4.5）。`buildConfirmationItems` は不一致件数の降順に並べるが、`mergeCorrections` が初回の並びをセッション中固定するため、初回解析時に不一致が 0 件だった曲は `partId` 昇順（＝楽譜順）のまま凍結される。ユーザーが並びの法則を学習できない

加えて `partId` のソートに `localeCompare` を使っているため、パートが 10 以上になると `P10 < P2` と並ぶ（メモ 4.2）。

## 実装対象の機能

### 1. 表示名モジュールの新設（メモ 6.6）

UI に出す文字列の「正」をコード側に置く。用語集と二重管理するとズレる（`G-clef-8vb` がその実例。メモ 4.7）。

- 音部記号の内部値 → 日本語表示名の対応表と変換関数
- `partId` → 「上から N 番目のパート」の変換関数
- 音部記号の確認状態（訂正済み／確認済み／要確認／未検査）の判定と表示名
- 件数の書式（単位付き、0 件は「—」）

### 2. 音部記号の日本語表示（メモ 6.1・6.2）

内部値（`TREBLE` 等）を画面に出さず、日本語のみを表示する。`ALTO` / `TENOR` はどちらもハ音記号であり合唱団員が日常的に出会う記号ではないため、線の位置まで書いて区別できるようにする。

| 内部値          | 表示                                   |
| --------------- | -------------------------------------- |
| `TREBLE`        | ト音記号                               |
| `BASS`          | ヘ音記号                               |
| `ALTO`          | アルト記号（ハ音記号・第3線）          |
| `TENOR`         | テノール記号（ハ音記号・第4線）        |
| `TREBLE_DOWN_8` | オクターヴ下ト音記号（テノールで頻出） |
| `UNKNOWN`       | 読み取れませんでした                   |

### 3. `UNKNOWN` を「未検査」として扱う（メモ 6.5）

「確認済み」「要確認」とは別の状態として表示し、**確認が必要な件数にも算入する**。ユーザーが正しい音部記号を選べば `corrections` が `staff.clefKind` を上書きし、クロスチェックが実際に走るようになる（訂正に具体的な効果がある）。

### 4. 並び順を楽譜順（上から下）に固定（メモ 6.3）

不一致件数の降順ソートを廃止し、`partId` の**自然順**（数値部分を数値として比較）に固定する。「不一致のある行を見つけやすくする」目的はソート以外の手段（バッジ・サマリ文）で達成する。並びが決定的になるため、`mergeCorrections` の並び凍結ロジックは不要になる。

### 5. 数値への単位・文脈の付与（メモ 6.4・施策 4/5）

- 音高の不一致: 単位を付け、0 件は「—」にする。**分母は出さない**（ユーザーが分母を持っており、意思決定を変えず、むしろ「0.7% なら無視でよい」と誤誘導しうるため）
- 対象の段数: 「全 12 段のうち 10 段」の形にし、1 行の訂正が何段に波及するかを文章で補う

### 6. 「譜表」「システム」を UI から追放（メモ 6.1）

- 「譜表」→「パート」
- 「システム」→「段」
- 画面タイトル「譜表構造の確認」→「楽譜の構成の確認」

### 7. 構造確認画面の再構成（施策 8/9）

- 訂正できる項目と、報告のみの項目（自動処理した内容）を分離し、後者は折りたたむ
- `inconsistentSystemStaffCount` の `(1, 1, 1, 1, 4, 4)` を日本語化し、インチピットに言及して「多くの場合そのまま進めてよい」旨を書く
- 問題 0 件時は「このまま進めます」と言い切る

### 8. 全画面共通ルール: `h1` 直下に「あなたが今すべきこと」を 1 文（施策 10）

Home / OmrProgress / StructureConfirm / ClefKeyConfirm / Editor の 5 画面すべてに適用する。

### 9. 永続ドキュメントの更新（メモ 8 章）

- 用語集: 「システム（段）/ 譜表 / 小節」に説明を追加、「パート」を新規追加、「オクターブ下ト音記号」の英語表記を実装（`TREBLE_DOWN_8`）に合わせる、音部記号の確認状態を追加、「確認項目」の表現を見直す
- 機能設計書: 並び順の方針変更（不一致降順 → 楽譜順）と画面表示の記述を実態に合わせる
- リポジトリ構造定義書: 新設する表示名モジュールの置き場所を追記

## 受け入れ条件

### 表示名モジュール

- [ ] 音部記号 6 種（`TREBLE` / `BASS` / `ALTO` / `TENOR` / `TREBLE_DOWN_8` / `UNKNOWN`）が上表のとおり日本語に変換される
- [ ] Audiveris の別名（`G_CLEF` / `F_CLEF`）も日本語に変換される（同義のため同じ表示名）
- [ ] 表にない未知の内部値でも内部値を画面に出さない
- [ ] `partId` が `P1` → 「上から1番目のパート」、`P12` → 「上から12番目のパート」になる
- [ ] `partId` が `null`・`P<数字>` 以外の形式でも破綻しない
- [ ] 確認状態が「訂正済み／確認済み／要確認／未検査」の 4 値に決まる

### 確認画面（ClefKeyConfirm）

- [ ] 画面に `P1` / `TREBLE` / `UNKNOWN` / `TREBLE_DOWN_8` のいずれの内部識別子も現れない
- [ ] `UNKNOWN` の行が「未検査」と表示され、確認が必要な件数に算入される
- [ ] 不一致 0 件の行の不一致欄が「—」になる
- [ ] 対象の段数が「全 N 段のうち M 段」の形で表示される
- [ ] 要確認・未検査の行にバッジが付く
- [ ] `h1` 直下に「今すべきこと」の 1 文がある
- [ ] サマリ文が「どこを見ればよいか」まで言い切る形になっている

### 並び順

- [ ] `buildConfirmationItems` の結果が `partId` の自然順で並ぶ（`P2` が `P10` より前）
- [ ] 不一致件数は並び順に影響しない

### 構造確認画面（StructureConfirm）

- [ ] 画面に「譜表」「システム」の語が現れない
- [ ] 訂正できる項目と報告のみの項目が分かれて表示される
- [ ] 報告のみの項目は折りたたまれている
- [ ] `inconsistentSystemStaffCount` の説明にインチピットへの言及がある
- [ ] 問題 0 件時に「このまま進めます」と言い切る
- [ ] `h1` 直下に「今すべきこと」の 1 文がある

## 成功指標

メモ 9 章の合格条件を満たすこと:

> **合唱経験はあるが OMR も MusicXML も知らない人**に画面を見せ、**5 秒以内に「今わたしは何をすればよいか」に答えられるか**

自動テストで機械的に確認できる代理指標として、次を用いる。

- 確認画面のレンダリング結果に内部識別子（`P1` / `TREBLE` / `UNKNOWN` / `TREBLE_DOWN_8`）が 1 つも含まれない
- 各画面が `h1` 直下に行動を促す 1 文を持つ

## スコープ外

以下はこのフェーズでは実装しません（メモ 10 章の未決事項）:

- **音部記号の切り抜き画像表示**: `clipRect` は既にあるが、表示には PDF.js の導入が必要で Editor のビューアと同時に入る想定
- **パート名のユーザー命名**（S/A/T/B の割り当て）: 語彙置換だけで目的の大半が達成できるため見送る
- **2 段譜・ピアノ伴奏の扱い**: `docs/` に記述のない未定義領域。扱うと決めた時点で UI 用語を見直す
- **上級者向けの内部値のログ／エクスポート出力**（メモ 6.1 の補足）: 本作業では画面から内部値を外すところまでとする
- スタイルシートの導入。本アプリは現状 CSS を持たないため、強調は文字（バッジ）とセマンティックな要素で表現する
