### 学んだこと

**技術的な学び**:

- **`localeCompare` は「番号付き ID」の順序比較に使ってはいけない**。`P10 < P2` になる。
  実データが 17 パートあるプロジェクトで、テストが 3 パートしか使っていなかったため見逃されていた。
  今回追加した `P10` を含むテストのように、**桁上がりをまたぐケースを最初から入れる**必要がある
- **「0」という表示は、それが何を意味するかまで決めないと嘘になりうる**。`UNKNOWN` の
  `mismatchCount: 0` は「検算して問題なし」ではなく「検算していない」だった。判定順序で
  `unchecked` を `mismatchCount` より先に見るだけで区別できるが、**先に状態の定義を書かないと
  この順序の重要性に気づけない**（design.md に状態表を書いたのが効いた）
- **「Xのとき検算が走らない」を実装するときは、X を条件式ではなく*関数*から逆算する**。
  今回は「`UNKNOWN` なら未検査」と条件を写したが、真の条件は `headStepOctave` が `null` を返す
  ケース全体（`clefKind === null` **と** 中線の定義が無い kind）だった。
  参照先の関数の early return を**全部**読むまで、条件を写したことにはならない
- **表示の分子と分母は、単位が同じであることを型か関数名で保証する**。
  `staffCoverageLabel(item.staffRefs.length, totalSystems)` は譜表数と段数を並べており、
  v1 の開離譜では偶然一致するため実データでもテストでも表面化しなかった
- **`shared/` に実装ロジックを置かない規約は、少量の重複と引き換えに境界を守る**。
  `partNumberOf` を domain と renderer の両方に置くのは一見冗長だが、共有しようとすると
  必ずどちらかの層がもう一方を import することになる。5 行の重複を受け入れるほうが安い
- CSS を持たないアプリでも、**文字（`⚠`）とセマンティックな列でバッジは成立する**。
  色に頼らない分、アクセシビリティ上もむしろ望ましい

**プロセス上の改善点**:

- **壁打ちメモが調査の実測値（実プロジェクト 4 件の `project.json`）を持っていたため、
  実装中に方針を迷う場面がほぼ無かった**。特に「なぜ分母を出さないか」「なぜ楽譜順か」は
  実装者が独断で決めると揺れる種類の判断で、根拠つきで先に決まっていた価値が大きい
- 表示名モジュールを最初に作ったため、以降の画面変更が「呼ぶだけ」になった。
  **翻訳の一覧性が上がり、内部値の漏れをテストで機械的に潰せた**（画面テキスト全体に
  内部識別子が含まれないことを検証するテストは、この集約なしには書けない）
- tasklist.md をフェーズ単位で一括更新したが、フェーズ内のタスク粒度が細かいため
  1 タスクずつの更新は冗長だった。フェーズ完了時の一括更新で進捗の可視性は十分保てた

### 次回への改善提案

- **文言変更は「テストが文言を固定している箇所」の棚卸しから始めると速い**。今回は
  `grep` で画面文言を検索してから着手したが、`App.test.tsx` の遷移テストは後から見つかった。
  最初に `tests/unit/renderer/` 全体を対象に変更予定の文字列を検索しておくとよい
- **ドキュメントの「未実装の姿」と「実装の姿」の乖離は、隣接する変更のついでに直すのが安い**。
  今回 StructureConfirm の UI設計節がそうだった。次回も、触った画面の設計記述は実態と突き合わせる
- 残った内部識別子の露出が 1 箇所ある: `Editor.tsx` の「適用されなかった訂正」が
