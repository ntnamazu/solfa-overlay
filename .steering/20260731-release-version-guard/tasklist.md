## 🚨 タスク完全完了の原則

**このファイルの全タスクが完了するまで作業を継続すること**

### 必須ルール

- **全てのタスクを`[x]`にすること**
- 「時間の都合により別タスクとして実施予定」は禁止
- 「実装が複雑すぎるため後回し」は禁止
- 未完了タスク（`[ ]`）を残したまま作業を終了しない

### 実装可能なタスクのみを計画

- 計画段階で「実装可能なタスク」のみをリストアップ
- 「将来やるかもしれないタスク」は含めない
- 「検討中のタスク」は含めない

### タスクスキップが許可される唯一のケース

以下の技術的理由に該当する場合のみスキップ可能:

- 実装方針の変更により、機能自体が不要になった
- アーキテクチャ変更により、別の実装方法に置き換わった
- 依存関係の変更により、タスクが実行不可能になった

スキップ時は必ず理由を明記:

```markdown
- [x] ~~タスク名~~（実装方針変更により不要: 具体的な技術的理由）
```

### タスクが大きすぎる場合

- タスクを小さなサブタスクに分割
- 分割したサブタスクをこのファイルに追加
- サブタスクを1つずつ完了させる

### 計画と実績の差分

**計画と異なった点**:

- **設計時に書いたコメント案がそのままでは不適切だった**。design.md のコード例では、インジェクション対策の説明を「`${{ github.ref_name }}` を run: に直接埋め込まない」と、**危険な書き方そのものを YAML コメント内に例示**していた。YAML コメントはパース時に破棄されるため実害はないが、`grep '\${{'` のような機械的な検査で誤検出を招き、コメントを読んだ人が誤って真似る余地も残る。実装時に「github.ref_name のテンプレート補間を run: に直接埋め込まない」という散文へ書き換えた。**危険な記法は、それを禁じる文脈であってもリポジトリに書かない**ほうがよい。
- **`develop` の `release.yml` には `--publish never` が入っていなかった**。`fix/release-implicit-publish`（コミット 972b116）は `docs/ui-wording-improvement` ブランチ上にあり、まだ `develop` へマージされていない。同じファイルの別の箇所（`dist:win` 行付近 vs 冒頭の検証ステップ）を触るためマージ自体は競合しない見込みだが、**ブランチを切る前に対象ファイルの現在の内容を確認する**必要があった。

**新たに必要になったタスク**:

- **検証ロジックの模擬実行を、yaml から `run:` 本文を抽出して行う方式に変更**。当初は「同じロジックをローカルで実行する」としか決めておらず、手でコピーしたスクリプトを検証すると**本物とは別物を検証してしまう**危険があった。`js-yaml` でパースして `steps[].run` をそのまま `bash` に流す方式に改め、検証対象と実物の同一性を担保した。
- **プレリリースタグのケース（ケース4）を追加**。design.md の「将来の拡張性」で「プレリリースタグにも追加変更なしで対応できる」と書いた主張を、実際に `v0.1.0-beta.1` で確かめた（`package.json` が `0.1.0` のため不一致検出＝設計どおり）。ドキュメントに書いた主張は検証しておく。
- **prettier の状態確認**。`npx prettier --check` が README を警告したが、`git show HEAD:README.md` を同じチェックに通して**変更前から未整形だった**（「動作要件」表の桁揃え）ことを確認し、今回の diff を汚さないため手を付けない判断をした。既存の乱れと自分が持ち込んだ乱れの切り分けは、`HEAD` の内容を同じ検査に通せば機械的にできる。

### 学んだこと

**技術的な学び**:

- **`windows-latest` の既定シェルは PowerShell**。`${VAR#v}` のようなパラメータ展開や `[ ... ]` を使う以上、`shell: bash` の明示は必須（Git Bash がランナーに同梱されている）。Linux ランナーの感覚でスクリプトを書くと、Windows ジョブでのみ落ちる。
- **`${GITHUB_REF_NAME#v}` は「先頭が `v` のときだけ 1 文字削る」**（`#` は最短前方一致）。`v` を含まないタグ名が来ても壊れず、単に不一致として検出される。ケース3（`GITHUB_REF_NAME=0.1.0`）で挙動を確認した。
- **バージョンの検証は「置く場所」で価値が変わる**。同じ 1 ステップでも、`fetch-resources`（Audiveris MSI の DL・`msiexec /a` 展開）と `dist:win` の**前**に置くか後に置くかで、失敗が分かるまでの待ち時間が桁違いになる。fail fast は「落ちること」より「早く落ちること」に意味がある。
- **バージョン番号の同期は「自動更新」ではなく「検証」で解くほうが素直**。CI がタグから `package.json` を書き換える方式は、コミット履歴に残る値と配布物の値がズレる余地を作る。値の出どころを 1 つに固定し、そこと食い違う入力を弾く形にすると、情報源の一意性が保たれる。

**プロセス上の改善点**:

- **受け入れ条件を「パーサで機械照合できる形」で書いたのが効いた**。`js-yaml` でワークフローを読み、ステップの順序（guard=2 < npm ci=3 < fetch-resources=4 < dist:win=5）や `shell` の値、`run` 本文の内容を 1 スクリプトで一括照合できた。YAML 設定ファイルの変更も、目視ではなく機械で検証できる。
- **調査結果（バージョンの伝言ゲーム経路）を requirements.md の「背景」に経路図として残した**のがよかった。`package.json` → `app.getVersion()` → IPC → preload → Home 画面という 5 段の経路は、次に誰かが「この表示はどこから来ているのか」を追うときの地図になる。
